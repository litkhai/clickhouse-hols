Distinct-count state size in materialized-view rollups

A per-minute rollup fed by a materialized view into an AggregatingMergeTree usually holds a few sums and one distinct count (uniqState). This lab measures how much of such a rollup that one column takes, whether a narrower input type (UInt32 instead of UInt64 or String) makes it smaller, what uniqCombined, uniqCombined(12), uniqHLL12 and uniqExact cost and how far off they are, how a 10-minute rollup fed from the 1-minute rollup (cascading materialized view) compares, and what each choice does to a Top 10 / Bottom 10 query over the last hour. Synthetic data on one local container; nothing here comes from a production system.

Cascading materialized views with TTL for retention are in workload/cascading-mv-ttl; this lab does not repeat that.

Run it

cd workload/mv-uniq-state-size
./run.sh                                        # fresh container, every NN-*.sql, 06-topn.sql five times
                                                # -> results/<version>.txt; about 2.5 minutes (2026-11-05, 12 CPUs)
KEEP=1 ./run.sh                                 # leave the container (musz-<tag>) running afterwards
tools/hol run workload/mv-uniq-state-size       # from the repository root: every file once, must not raise

run.sh needs only Docker. It takes the image tag from lab.yaml, starts the container the way tools/hol up does (no published ports), writes the date, version(), host CPU, Docker VM size and the CPU% of every other running container at the start and before the timing runs into the results file, runs each file with clickhouse-client --echo, and removes the container (and its volume) at the end. 99-cleanup.sql is skipped by run.sh and run by tools/hol.

On this build the uniq columns are stored as AggregateFunction(1, uniq, …), a state version, although 01-setup.sql declares AggregateFunction(uniq, …); the other functions have none. The built-in description of uniq (system.functions, read 2026-11-05) says servers from 26.8 also keep a small sample of 64-bit hashes and that states written by older servers carry none.

The cascade (05-cascade-check.sql). The 10-minute rollup fed from the 1-minute rollup against 10-minute groups computed from the raw rows: 144,000 groups on both sides, 0 differences in events, uniqExact, uniq, uniqCombined and uniqHLL12; uniqCombined(12) differs in 20 groups, every one of them with exactly 256 true distinct values, by at most 10. The negative control, adding up the per-minute distinct counts, is wrong in 143,945 of 144,000 groups and 1.53 times the true count on average.

The same direct 10-minute computation repeated: uniq, uniqCombined and uniqHLL12 gave the same result fingerprint in all five runs; uniqCombined(12) gave three different fingerprints in the three runs with the default max_threads and the same one in the two runs with max_threads = 1. So the 20 is not a cascade error: uniqCombined(12) itself returns different answers for the same data, at its switch point. The built-in description says uniqCombined "provides the result deterministically (it does not depend on the query processing order)".

What the numbers say

  • One distinct-count column is about 91% of a 1-minute rollup and 98% of a 10-minute one here, whichever function it uses. The other columns are 13.11 MiB against 131.22 MiB for uniq.
  • A narrower input type does not shrink uniq (4 bytes per distinct value for String, UInt64 and UInt32; Nullable adds one byte per state). It shrinks uniqExact (16 / 8 / 4 bytes per value) and the small-set form of uniqCombined over String (twice the integer size).
  • The fixed-size states (uniqCombined(12) and uniqHLL12, 2,651 bytes) are smaller than uniq only above 600–700 distinct values per group. With a median of 11 per 1-minute group, uniqCombined(12) saved 8% and uniqHLL12 cost 32% more (and was the slowest to query: 480 MiB to decompress).
  • A 10-minute rollup does not cost a tenth: the state columns were 0.56 of the 1-minute ones while the rows were 0.1. A 1-minute rollup without the distinct count is 13.11 MiB.
  • The cascade is correct for uniqExact, uniq, uniqCombined and uniqHLL12. Check it with a query like the one in 05-cascade-check.sql and its negative control.
  • At 12 million raw rows per hour on 12 CPUs, the raw table answered the last-hour Top/Bottom 10 as fast as the 1-minute rollup (48–50 ms against 49–72 ms for the uniq-sized states) while reading 2.7 times the bytes; the 10-minute rollup took 34–38 ms. This lab does not measure how the gap grows with the raw volume.

Limits

One build, one machine, synthetic data: users uniform over 500,000, each fixed to one page, so the distinct count per group follows the page skew and not a real workload. Sizes are after OPTIMIZE … FINAL; a live rollup also holds unmerged partial states. Timings are warm (median of five) with other containers running. The uniqCombined(12) difference count changes from run to run (see above).

materialized view로 AggregatingMergeTree에 쌓는 1분 롤업에는 보통 합계 몇 개와 고유 수(uniqState) 하나가 들어갑니다. 이 실습은 그 고유 수 컬럼 하나가 롤업의 얼마를 차지하는지, 입력 타입을 좁히면(UInt64나 String 대신 UInt32) 작아지는지, uniqCombined · uniqCombined(12) · uniqHLL12 · uniqExact의 크기와 오차, 1분 롤업에서 이어 만든 10분 롤업(cascading materialized view)의 크기와 정확성, 그리고 각 선택이 최근 1시간 Top 10 / Bottom 10 조회에 주는 영향을 잽니다. 로컬 컨테이너 하나와 합성 데이터만 씁니다. 운영 시스템의 데이터는 없습니다.

TTL로 보관 기간을 관리하는 cascading materialized view는 workload/cascading-mv-ttl에 있고, 여기서 반복하지 않습니다.

이 빌드는 uniq 컬럼을 AggregateFunction(1, uniq, …), 즉 상태 버전을 붙여 저장합니다. 01-setup.sql은 AggregateFunction(uniq, …)로 선언했고, 다른 함수에는 버전이 붙지 않습니다. uniq의 내장 설명 (system.functions, 2026-11-05에 읽음)에 따르면 26.8부터 서버가 64비트 해시의 작은 표본도 함께 두고, 그보다 오래된 서버가 쓴 상태에는 그 표본이 없습니다.

cascade(05-cascade-check.sql). 1분 롤업에서 받은 10분 롤업과 원본에서 바로 계산한 10분 그룹: 양쪽 모두 그룹 144,000개, events · uniqExact · uniq · uniqCombined · uniqHLL12 차이 0. uniqCombined(12)는 20개 그룹에서 달랐고, 모두 실제 고유값이 정확히 256인 그룹이었으며 차이는 최대 10이었습니다. 음성 대조(분당 고유 수를 더하기)는 144,000개 중 143,945개 그룹에서 틀렸고 평균 실제 값의 1.53배였습니다.

같은 직접 계산을 반복하면 uniq · uniqCombined · uniqHLL12는 다섯 번 모두 같은 결과 지문을 냈고, uniqCombined(12)는 기본 max_threads로 세 번 돌린 결과가 셋 다 달랐으며 max_threads = 1로 두 번 돌린 결과는 같았습니다. 그러니 20개는 cascade의 오류가 아니라, uniqCombined(12)가 전환 지점에서 같은 데이터에 다른 답을 내는 것입니다. 내장 설명은 uniqCombined가 "provides the result deterministically (it does not depend on the query processing order)"라고 적고 있습니다.

숫자가 말하는 것

  • 여기서 고유 수 컬럼 하나는 어떤 함수를 쓰든 1분 롤업의 약 91%, 10분 롤업의 98%였습니다. 나머지 컬럼은 13.11 MiB, uniq는 131.22 MiB입니다.
  • 입력 타입을 좁혀도 uniq는 줄지 않습니다(String · UInt64 · UInt32 모두 고유값당 4바이트, Nullable은 상태당 1바이트 추가). 줄어드는 것은 uniqExact(값당 16 / 8 / 4바이트)와 String 입력 uniqCombined의 작은 집합 형태(정수의 두 배)입니다.
  • 고정 크기 상태(uniqCombined(12), uniqHLL12, 2,651바이트)는 그룹당 고유값이 600–700을 넘어야 uniq보다 작습니다. 1분 그룹 중앙값이 11인 이 데이터에서 uniqCombined(12)는 8% 줄었고 uniqHLL12는 32% 커졌습니다 (조회도 가장 느렸습니다. 압축 해제 480 MiB).
  • 10분 롤업은 1/10이 아닙니다. 행은 0.1배인데 상태 컬럼은 0.56배였습니다. 고유 수가 없는 1분 롤업은 13.11 MiB입니다.
  • cascade는 uniqExact · uniq · uniqCombined · uniqHLL12에서 정확했습니다. 05-cascade-check.sql 같은 쿼리와 음성 대조로 확인합니다.
  • 12 CPU에서 시간당 원본 1,200만 행이면, 최근 1시간 Top/Bottom 10을 원본 테이블이 1분 롤업과 비슷한 시간에 답했습니다(48–50 ms, uniq 크기 상태는 49–72 ms). 읽은 바이트는 2.7배였습니다. 10분 롤업은 34–38 ms였습니다. 원본이 커질 때 이 차이가 어떻게 벌어지는지는 이 실습에서 재지 않았습니다.
