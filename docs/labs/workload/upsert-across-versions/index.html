Upsert, UPDATE and DELETE across ClickHouse versions

The same SQL for every way of changing rows in ClickHouse, run on six builds (the LTS lines 24.8, 25.3, 25.8, 26.3, 26.8 and the latest stable 26.10). For each way the runner records: does it run on that version (or which error code), how long it takes, what it writes (bytes, from system.part_log), how soon the change is visible, and what it costs later SELECTs. Nothing here is quoted from a changelog: every cell in RESULTS.md comes from a run, and the raw per-probe data (including query_log rows) is in results/<version>.json.

The ways: ReplacingMergeTree (with and without is_deleted), CollapsingMergeTree and VersionedCollapsingMergeTree, CoalescingMergeTree, classic ALTER TABLE ... UPDATE, the SQL UPDATE (patch parts), re-inserting with a higher version, on-the-fly mutations, and three kinds of DELETE.

Run it

cd workload/upsert-across-versions
./run_matrix.py                      # all six versions, about 17 minutes; pulls nothing, images must exist
./run_matrix.py --versions 26.10     # one version (prefix of a line in versions.txt)
./run_matrix.py --only 04            # one file or probe-id prefix; results merge into the JSON
./run_matrix.py --report-only        # rebuild RESULTS.md from results/*.json
tools/hol run workload/upsert-across-versions   # from the repository root: the SQL on 26.10 only, must not raise

versions.txt pins the exact tags, oldest first. run_matrix.py is the runner of workload/join-across-versions (same file; containers are named uav-<tag> here and jav-<tag> there). A statement preceded by -- probe: <id> [repeat=N] [value] is a probe, the others are setup; value puts the first result row in the table cell. -- settings: a, b lists settings to look up in system.settings, then in system.merge_tree_settings (shown as [table]). Each statement runs in its own clickhouse-client call, so there is no bare SET.

Probes

File What it does
01-replacing.sql ReplacingMergeTree(ver) and (ver, is_deleted), 2M keys, then 1% re-written with a higher ver, 0.1% marked deleted: count() without and with FINAL, FINAL vs argMax ... GROUP BY (5 repeats), OPTIMIZE ... FINAL, FINAL CLEANUP
02-collapsing.sql CollapsingMergeTree and VersionedCollapsingMergeTree with the cancel row inserted before the state row; a state-first control
03-coalescing.sql CoalescingMergeTree with sparse inserts vs the same inserts into ReplacingMergeTree
04-update-mechanisms.sql classic ALTER UPDATE, re-insert into ReplacingMergeTree and patch-part UPDATE, each at 1 row, 1% and 10% of 2M rows (one table each): duration, bytes written, patch parts, then a full-scan SELECT sum(v) (5 repeats) against untouched control tables
05-on-the-fly.sql a pending mutation (SYSTEM STOP MERGES, mutations_sync = 0) read with apply_mutations_on_fly 1 and 0
06-patch-accumulation.sql 50 successive one-row UPDATEs: patch-part count, scan and point read after 1, 10, 50; then OPTIMIZE ... FINAL and ALTER TABLE ... APPLY PATCHES
07-delete.sql ALTER ... DELETE, DELETE FROM, DELETE FROM with lightweight_delete_mode = 'lightweight_update': duration, bytes, count() with apply_deleted_mask 1 and 0
08-scale.sql the read-side cost of file 04 at 20M rows (a scan of 130 to 480 ms): classic ALTER UPDATE, patch-part UPDATE and re-insert at 1% and 10%, a full-scan aggregate and a 100,000-row range read (5 repeats each) against untouched controls
errors/01-expected-failures.sql statements that fail even on 26.10 (UPDATE without block columns, forced lightweight DELETE, CLEANUP without its table setting, UPDATE of a sort-key column). tools/hol does not run this directory; the runner does

Every probe in the top-level files succeeds on 26.10 (tools/hol run stops at the first exception). Failures on older versions are the result, shown as ✗ Code N (56 UNKNOWN_STORAGE, 62 SYNTAX_ERROR, 115 UNKNOWN_SETTING, 344 SUPPORT_IS_DISABLED, 420 CANNOT_UPDATE_COLUMN, 48 NOT_IMPLEMENTED).

What changed between versions

Written only from RESULTS.md (run on 2026-11-04, 12 CPUs, 15.6 GiB Docker VM). Other containers were running during the whole run (RESULTS.md lists their CPU% per version; the 26.10 run overlapped with about 300% of other load), and most timed probes take 4 to 30 ms, so differences of a few milliseconds are not used below.

  • Patch-part UPDATE. Syntax error (Code 62) on 24.8.14.39 and 25.3.14.14; it runs from 25.8.33.6. It needs a table created with enable_block_number_column = 1 and enable_block_offset_column = 1 (without them: Code 48, "Lightweight updates are supported only for tables with materialized _block_number column", same on 25.8 to 26.10; err-update-no-block-columns). It needs no session setting: 04-pu-no-setting (no SETTINGS clause) runs on 25.8 to 26.10. The setting allow_experimental_lightweight_update exists from 25.8 as Beta and as Production on 26.10. UPDATE of a sort-key column fails with Code 420 (patch part and classic mutation alike).
  • How a patch part looks. In system.parts, a patch part has a name starting with patch-, for example patch-<hash>-all_4_4_0_3, and part_type Compact. In system.part_log it is a NewPart. There is no patch column in system.parts; the probes find them with startsWith(name, 'patch-').
  • Lightweight DELETE. DELETE FROM runs on all six versions. lightweight_delete_mode exists from 25.8 (default alter_update; on 24.8 and 25.3 setting it is Code 115). In the default mode DELETE FROM is a MutatePart that writes about 11 KB (24.8) to 18 KB (26.10) for 1% of 2M rows; ALTER ... DELETE writes 16 MB. With lightweight_delete_mode = 'lightweight_update' on a table with the block columns the server writes a patch part instead (07-delete-patch-bytes: 5 KB on 25.8 and 26.3, 92 KB on 26.8 and 26.10, no MutatePart). lightweight_update_force on a table without the block columns fails with Code 344 (err-delete-force-no-block-columns). With apply_deleted_mask = 0 the deleted rows are back (count() 2,000,000 against 1,980,000) on every version, and for the patch mode from 25.8.
  • Patch bytes. For the same 1% update the patch part is 93 KB (10%: 845 KB) on 25.8.33.6 and 26.3.62.3; on 26.8.36.3 and 26.10.3.7 they are 180 KB and 1.65 MB.
  • On-the-fly mutations. apply_mutations_on_fly = 1 returns the new value on 25.3.14.14 and later; on 24.8.14.39 the setting exists but the read still returns the old value (05-read-on-fly).
  • APPLY PATCHES. ALTER TABLE ... APPLY PATCHES ran on 25.8 to 26.10. After 50 patches, OPTIMIZE ... FINAL renamed the base part (all_1_2_1 to all_1_2_2_101) and left one active patch part holding the 50 rows; APPLY PATCHES renamed it again (..._103). On 25.8.33.6 no patch part was active afterwards; on 26.3.62.3, 26.8.36.3 and 26.10.3.7 one patch part with 50 rows stayed active. Scan and point-read results are identical in all steps.
  • ReplacingMergeTree. Same results on all six versions: 2,020,000 rows without FINAL, 2,000,000 with it; a plain OPTIMIZE FINAL on the is_deleted table leaves the 2,000 deleted rows (2,000,000 physical rows); OPTIMIZE ... FINAL CLEANUP removes them (1,998,000) but only when the table was created with allow_experimental_replacing_merge_with_cleanup = 1; without it, Code 344 on every version.
  • CollapsingMergeTree, cancel row first. Same on all six versions. After OPTIMIZE ... FINAL the table keeps 101,000 rows: for each of the 1,000 cancelled keys both the -1 and the +1 row stay (sum(sign) is 99,000 and the -1 count is 1,000). FINAL before the merge returns 100,000 rows. HAVING sum(sign) > 0 returns the 99,000 correct keys. The state-first control and VersionedCollapsingMergeTree with the cancel row first both end with 99,000 rows.
  • CoalescingMergeTree. Code 56 (unknown engine) on 24.8.14.39 and 25.3.14.14; from 25.8.33.6 the three sparse inserts become one row per key with all three columns set under FINAL and after OPTIMIZE, where ReplacingMergeTree keeps only the last insert's column.

1 row / 1% / 10% on 2M rows

Bytes written come from system.part_log (ProfileEvents['WriteBufferFromFileDescriptorWriteBytes']), the update times are single runs, and the SELECT sum(v) columns are median (fastest) of 5 repeats in ms. Controls: untouched MergeTree 4 (4) ms on 26.10 and 9 (5) on 24.8; untouched ReplacingMergeTree with FINAL 5 (4) on 26.10. Values are 26.10.3.7; the oldest build where the mechanism runs is in brackets (24.8.14.39 for classic and re-insert, 25.8.33.6 for patch parts).

Reading the table: the classic mutation rewrites the whole v column (about 8 MB) at every fraction, the re-insert and the patch part write roughly in proportion to the changed rows. After the change, a scan of a mutated table costs the same as the control within the 1 ms resolution; the re-insert needs FINAL (14 to 16 ms on 26.10 against 5 ms for an untouched ReplacingMergeTree with FINAL; without FINAL it is fast and wrong, the sum counts the re-written keys twice); the patch-part table reads 12 to 17 ms against 4 ms for the control while the patch is still a separate part. The update times of the re-insert on 26.10 and 24.8 differ by more than their difference in work, so they are noise; do not rank mechanisms by them. Only a 2M-row table and one data layout (the changed rows spread over every granule at 1% and 10%) were measured; the 10% threshold the lab was started from is not tested by anything beyond these three fractions.

Read cost at 20M rows (08-scale.sql)

The same three mechanisms at 10x the size, so a scan takes 130 to 480 ms and the 1 ms resolution no longer matters. Each table is one part before the change, the patch-part and re-insert tables have merges stopped, and the re-insert tables are read with FINAL. The scan is SELECT sum(sipHash64(v, s)), uniq(v) over every row; the range read is the same aggregate over 100,000 ids on the sort key. Cells are median (fastest) of 5 repeats in ms, 26.10.3.7 first and the oldest build where the mechanism runs in brackets (24.8.14.39; 25.8.33.6 for patch parts). The run took 74 to 121 s per version; other containers were running (RESULTS.md has their CPU%, total 88% to 459% of 1200%), so read differences smaller than about 30% as noise.

The control for the re-insert column is an untouched ReplacingMergeTree read with FINAL: 154 (131) on 26.10.3.7 and 170 (149) on 24.8.14.39 for the full scan, 3 (3) and 8 (4) for the range. The untouched MergeTree is the control for the other columns. Without FINAL, the re-insert table scans in 157 (148) ms on 26.10 but returns a wrong sum.

What the 26.10 numbers show: a classic-mutated table scans like the control; the patch-part table scans about 1.4x to 1.6x the control, and the FINAL table about 1.7x to 1.8x (against the untouched FINAL table, 154 (131), about 1.7x). Range reads on the sort key stay in single-digit milliseconds for every mechanism. The updates themselves (single runs, 26.10.3.7): classic 1.37 s (1%) and 0.80 s (10%), writing 20 MB for both; patch part 125 ms and 269 ms, writing 1.8 MB and 16 MB; re-insert 63 ms and 255 ms, writing 1.8 MB and 9.2 MB.

What changes between builds, from the same file:

  • Patch part, bytes written. 916 KB (1%) and 8.4 MB (10%) on 25.8.33.6 and 26.3.62.3; 1.79 MB and 16.4 MB on 26.8.36.3 and 26.10.3.7, for the same changed rows (200,000 and 2,000,000).
  • Patch part, update time (1% / 10%). 137 / 734 ms on 25.8, 141 / 553 ms on 26.3, 100 / 832 ms on 26.8, 125 / 269 ms on 26.10 (single runs).
  • Patch part, scan (1% / 10%). 186 (173) / 270 (229) on 25.8 against a control of 252 (203); 367 (226) / 229 (160) on 26.3 against 147 (120); 281 (200) / 242 (213) on 26.8 against 209 (166); 202 (185) / 242 (204) on 26.10 against 148 (134). The control itself varies by 1.7x between builds on this loaded machine, so the overhead ratios of 25.8 to 26.8 are not reliable; these runs do not separate the builds.
  • Classic mutation, bytes written. 79 MB (1%) and 72 MB (10%) on 24.8 to 26.8; 20.5 MB and 19.6 MB on 26.10.3.7. At 2M rows (file 04) all six builds wrote 7 to 8 MB. This lab did not look into why.
  • Not available. Patch parts are Code 62 on 24.8 and 25.3, as in file 04; their classic and re-insert tables ran.

Not verified here

  • Distributed or replicated tables, SharedMergeTree and ClickHouse Cloud.
  • Tables larger than 20M rows, concurrent writers, and changed rows clustered in a few granules.
  • Wall-clock times: other containers were running (see RESULTS.md).

Verified on 24.8.14.39, 25.3.14.14, 25.8.33.6, 26.3.62.3, 26.8.36.3 and 26.10.3.7, 2026-11-04 (./run_matrix.py, all six; tools/hol run on 26.10.3.7).

ClickHouse에서 행을 바꾸는 모든 방법을 같은 SQL로 여섯 빌드(LTS 24.8, 25.3, 25.8, 26.3, 26.8과 최신 stable 26.10)에서 실행합니다. 방법마다 그 버전에서 실행되는지(안 되면 오류 코드), 걸리는 시간, 쓰는 양(system.part_log의 바이트), 변경이 보이기까지의 시간, 이후 SELECT에 드는 비용을 기록합니다. changelog를 인용한 내용은 없고, RESULTS.md의 모든 셀은 실행 결과입니다. 원시 데이터 (query_log 행 포함)는 results/<버전>.json에 있습니다.

대상: ReplacingMergeTree(is_deleted 유무), CollapsingMergeTree, VersionedCollapsingMergeTree, CoalescingMergeTree, 기존 ALTER TABLE ... UPDATE, SQL UPDATE(패치 파트), 더 높은 버전으로 재삽입, on-the-fly 뮤테이션, 세 종류의 DELETE.

실행

cd workload/upsert-across-versions
./run_matrix.py                      # 여섯 버전 전부, 약 17분. 이미지는 미리 받아 둬야 함
./run_matrix.py --versions 26.10     # 한 버전(versions.txt 줄의 접두사)
./run_matrix.py --only 04            # 파일 또는 probe id 접두사. 결과는 JSON에 병합
./run_matrix.py --report-only        # results/*.json으로 RESULTS.md 재생성
tools/hol run workload/upsert-across-versions   # 저장소 루트에서: 26.10에서만 실행, 예외가 없어야 함

versions.txt는 정확한 태그를 오래된 순으로 고정합니다. run_matrix.py는 workload/join-across-versions와 같은 파일입니다(컨테이너 이름은 여기서 uav-<태그>, 거기서는 jav-<태그>). -- probe: <id> [repeat=N] [value]가 앞에 붙은 문장이 probe이고 나머지는 준비 문장입니다. value는 첫 결과 행을 표 셀에 넣습니다. -- settings: a, b는 system.settings, 없으면 system.merge_tree_settings([table]로 표시)에서 찾습니다. 문장마다 clickhouse-client를 따로 호출하므로 단독 SET은 쓰지 않습니다.

버전별 변화

RESULTS.md에서만 가져온 내용입니다(2026-11-04 실행, CPU 12개, Docker VM 15.6 GiB). 실행 내내 다른 컨테이너가 돌고 있었고(버전별 CPU%는 RESULTS.md에 있고 26.10 실행은 약 300%의 다른 부하와 겹쳤습니다), 시간을 잰 대부분의 probe가 4~30 ms라서 몇 ms 차이는 아래에서 근거로 쓰지 않습니다.

  • 패치 파트 UPDATE. 24.8.14.39와 25.3.14.14에서는 문법 오류(Code 62), 25.8.33.6부터 실행됩니다. enable_block_number_column = 1, enable_block_offset_column = 1로 만든 테이블이 필요합니다(없으면 Code 48, 25.8~26.10 동일, err-update-no-block-columns). 세션 설정은 필요 없습니다: SETTINGS 절 없는 04-pu-no-setting이 25.8~26.10에서 실행됩니다. allow_experimental_lightweight_update는 25.8부터 있고 Beta, 26.10에서는 Production입니다. 정렬 키 컬럼의 UPDATE는 패치 파트와 기존 뮤테이션 모두 Code 420으로 실패합니다.
  • 패치 파트의 모습. system.parts에서 이름이 patch-로 시작하고(예: patch-<해시>-all_4_4_0_3) part_type은 Compact입니다. system.part_log에서는 NewPart입니다. system.parts에 패치 전용 컬럼은 없어서 probe는 startsWith(name, 'patch-')로 찾습니다.
  • Lightweight DELETE. DELETE FROM은 여섯 버전 모두에서 실행됩니다. lightweight_delete_mode는 25.8부터 있고(기본 alter_update, 24.8과 25.3에서 지정하면 Code 115) 기본 모드의 DELETE FROM은 200만 행의 1%에 대해 약 11 KB(24.8)~18 KB(26.10)를 쓰는 MutatePart이고, ALTER ... DELETE는 16 MB를 씁니다. 블록 컬럼이 있는 테이블에서 lightweight_delete_mode = 'lightweight_update'를 쓰면 패치 파트를 씁니다(07-delete-patch-bytes: 25.8과 26.3에서 5 KB, 26.8과 26.10에서 92 KB, MutatePart 없음). 블록 컬럼 없는 테이블에서 lightweight_update_force는 Code 344로 실패합니다 (err-delete-force-no-block-columns). apply_deleted_mask = 0이면 삭제한 행이 다시 보입니다 (count() 2,000,000 대 1,980,000). 모든 버전에서 같고 패치 모드는 25.8부터입니다.
  • 패치 바이트. 같은 1% 업데이트에서 패치 파트는 25.8.33.6과 26.3.62.3에서 93 KB(10%는 845 KB), 26.8.36.3과 26.10.3.7은 180 KB와 1.65 MB입니다.
  • On-the-fly 뮤테이션. apply_mutations_on_fly = 1은 25.3.14.14부터 새 값을 반환하고, 24.8.14.39는 설정은 있지만 읽으면 이전 값이 나옵니다(05-read-on-fly).
  • APPLY PATCHES. ALTER TABLE ... APPLY PATCHES는 25.8~26.10에서 실행됐습니다. 패치 50개 뒤 OPTIMIZE ... FINAL은 기본 파트 이름을 바꾸고(all_1_2_1에서 all_1_2_2_101) 50행을 담은 활성 패치 파트 하나를 남겼고, APPLY PATCHES는 다시 이름을 바꿨습니다(..._103). 25.8.33.6에서는 이후 활성 패치 파트가 없었고 26.3.62.3, 26.8.36.3, 26.10.3.7에서는 50행짜리 패치 파트 하나가 활성으로 남았습니다. 스캔과 포인트 읽기 결과는 모든 단계에서 같습니다.
  • ReplacingMergeTree. 여섯 버전 모두 같습니다: FINAL 없으면 2,020,000행, 있으면 2,000,000행. is_deleted 테이블의 일반 OPTIMIZE FINAL은 삭제 행 2,000개를 남기고(물리 2,000,000행), OPTIMIZE ... FINAL CLEANUP이 지웁니다(1,998,000). 단 테이블을 allow_experimental_replacing_merge_with_cleanup = 1로 만들었을 때만이고, 아니면 모든 버전에서 Code 344입니다.
  • 취소 행이 먼저인 CollapsingMergeTree. 여섯 버전 모두 같습니다. OPTIMIZE ... FINAL 뒤에도 101,000행이 남습니다. 취소된 1,000개 키마다 -1 행과 +1 행이 둘 다 남습니다(sum(sign)은 99,000, -1 행은 1,000개). 머지 전 FINAL은 100,000행을 반환합니다. HAVING sum(sign) > 0은 올바른 99,000개 키를 반환합니다. 상태 행을 먼저 넣은 대조군과, 취소 행이 먼저인 VersionedCollapsingMergeTree는 모두 99,000행으로 끝납니다.
  • CoalescingMergeTree. 24.8.14.39와 25.3.14.14에서는 Code 56(알 수 없는 엔진), 25.8.33.6부터 드문드문 넣은 세 INSERT가 FINAL과 OPTIMIZE 뒤에 세 컬럼이 모두 채워진 키당 한 행이 됩니다. ReplacingMergeTree는 마지막 INSERT의 컬럼만 남깁니다.

200만 행의 1행 / 1% / 10%

쓴 바이트는 system.part_log(ProfileEvents['WriteBufferFromFileDescriptorWriteBytes'])에서, 업데이트 시간은 단일 실행, SELECT sum(v)는 5회 반복의 중앙값(최솟값) ms입니다. 대조군: 건드리지 않은 MergeTree는 26.10에서 4 (4) ms, 24.8에서 9 (5), 건드리지 않은 ReplacingMergeTree의 FINAL은 26.10에서 5 (4). 값은 26.10.3.7이고 대괄호는 그 방법이 실행되는 가장 오래된 빌드(기존 방식과 재삽입은 24.8.14.39, 패치 파트는 25.8.33.6)입니다.

2,000만 행에서의 읽기 비용(08-scale.sql)

같은 세 방법을 10배 크기에서 측정해 스캔이 130~480 ms가 되므로 1 ms 해상도가 더는 문제가 되지 않습니다. 테이블마다 변경 전에는 파트 하나이고, 패치 파트와 재삽입 테이블은 머지를 멈췄으며, 재삽입 테이블은 FINAL로 읽습니다. 스캔은 전체 행에 대한 SELECT sum(sipHash64(v, s)), uniq(v), 범위 읽기는 정렬 키 기준 10만 id에 대한 같은 집계입니다. 셀은 5회 반복의 중앙값(최솟값) ms이며 26.10.3.7이 먼저이고 대괄호는 그 방법이 실행되는 가장 오래된 빌드(24.8.14.39, 패치 파트는 25.8.33.6)입니다. 버전당 74~121초가 걸렸고 다른 컨테이너가 돌고 있었으므로(CPU% 합계는 RESULTS.md, 1200% 중 88~459%) 약 30%보다 작은 차이는 잡음으로 보세요.

26.10 숫자가 보여 주는 것: 기존 뮤테이션을 한 테이블은 대조군과 같은 속도로 스캔되고, 패치 파트 테이블은 대조군의 약 1.4~1.6배, FINAL 테이블은 약 1.7~1.8배입니다(건드리지 않은 FINAL 테이블 154 (131) 기준으로는 약 1.7배). 정렬 키 범위 읽기는 모든 방법에서 한 자릿수 ms입니다. 업데이트 자체(단일 실행, 26.10.3.7): 기존 방식은 1%에 1.37초, 10%에 0.80초로 둘 다 20 MB를 쓰고, 패치 파트는 125 ms와 269 ms에 1.8 MB와 16 MB, 재삽입은 63 ms와 255 ms에 1.8 MB와 9.2 MB를 씁니다.

같은 파일에서 본 빌드 간 변화:

  • 패치 파트 쓴 바이트. 같은 바뀐 행(20만, 200만)에 대해 25.8.33.6과 26.3.62.3은 916 KB(1%)와 8.4 MB(10%), 26.8.36.3과 26.10.3.7은 1.79 MB와 16.4 MB입니다.
  • 패치 파트 업데이트 시간(1% / 10%). 25.8 137 / 734 ms, 26.3 141 / 553 ms, 26.8 100 / 832 ms, 26.10 125 / 269 ms(단일 실행).
  • 패치 파트 스캔(1% / 10%). 25.8 186 (173) / 270 (229), 대조군 252 (203). 26.3 367 (226) / 229 (160), 대조군 147 (120). 26.8 281 (200) / 242 (213), 대조군 209 (166). 26.10 202 (185) / 242 (204), 대조군 148 (134). 부하가 있는 이 머신에서 대조군 자체가 빌드 사이에 1.7배 달라지므로 25.8~26.8의 오버헤드 비율은 신뢰할 수 없고, 이 실행으로는 빌드를 구분할 수 없습니다.
  • 기존 뮤테이션 쓴 바이트. 24.8~26.8은 79 MB(1%), 72 MB(10%), 26.10.3.7은 20.5 MB, 19.6 MB입니다. 200만 행(파일 04)에서는 여섯 빌드 모두 7~8 MB였습니다. 이유는 이 실습에서 조사하지 않았습니다.
  • 불가. 패치 파트는 파일 04처럼 24.8과 25.3에서 Code 62이고, 그 빌드의 기존 방식과 재삽입 테이블은 실행됐습니다.
