JOIN across ClickHouse versions

The same JOIN SQL, run on six ClickHouse builds (the LTS lines 24.8, 25.3, 25.8, 26.3, 26.8 and the latest stable 26.10). For every probe and version the runner records: did it run (or which error code), how long, peak memory, rows read, and which join algorithm. Nothing here is quoted from a changelog: every cell in RESULTS.md comes from a run, and the raw per-probe data (including query_log rows, ProfileEvents and the first result rows) is in results/<version>.json.

Run it

cd workload/join-across-versions
./run_matrix.py                      # all six versions, about 4 minutes on a quiet machine (2026-11-05); pulls nothing, images must exist
./run_matrix.py --versions 26.10     # one version (prefix of a line in versions.txt)
./run_matrix.py --only 05            # one file or probe-id prefix; results merge into the JSON
./run_matrix.py --report-only        # rebuild RESULTS.md from results/*.json
tools/hol run workload/join-across-versions   # from the repository root: the SQL on 26.10 only, must not raise

versions.txt pins the exact tags, oldest first. The runner (Python 3 stdlib and the Docker CLI) starts one container per version like tools/hol up does, publishes no ports, runs every NN-*.sql and removes the container. It is generic: a statement preceded by -- probe: <id> [repeat=N] [show] [events] is a probe, the others are setup; -- settings: a, b in a file lists settings to look up in system.settings. A statement ends with ; at the end of a line (no line may end in ; inside a string literal). Each statement runs in its own clickhouse-client call, so the SQL uses no bare SET; settings are in each statement's SETTINGS.

Probes

File Probes Question
00-data.sql setup facts 5M rows, customers 500k with a ~200 byte comment, regions, bands, prices, contacts; numbers() + cityHash64, no rand()
01-hash-baseline.sql default / hash / parallel_hash big table left, small right: what does join_algorithm's default pick
02-join-side.sql control, big table on the right, swap disabled does the server put the small table on the build side by itself (query_plan_join_swap_table)
03-non-equi-on.sql range, arbitrary, LEFT arbitrary, equality+inequality (INNER/LEFT), with and without allow_experimental_join_condition which non-equi ON forms run
04-correlated-subquery.sql EXISTS, NOT EXISTS, scalar subquery in the select list correlated subqueries
05-runtime-filter.sql star join and a selective build side, default / on / off enable_join_runtime_filters: rows read, memory, ProfileEvents
06-memory-cap.sql uncapped peaks of the default, hash, partial_merge, grace_hash; grace_hash with 8 and 16 buckets and the default with max_bytes_before_external_join, under max_memory_usage = 800000000 which paths finish far below a cap their build side exceeds (5M customers_big rows, 1.6 to 1.9 GiB uncapped)
07-lazy-replication.sql many-to-many with a wide column, default / on / off enable_lazy_columns_replication
08-syntax.sql ASOF LEFT, LEFT SEMI, LEFT ANTI, PASTE, NATURAL, USING, FULL with join_use_nulls, LEFT JOIN LATERAL from which version each parses
09-explain.sql EXPLAIN actions = 1 of the runtime-filter, LATERAL and LEFT arbitrary-ON joins plan text, stored in the JSON
10-scale.sql 50M-row facts_big x 5M-row customers_big: big table left, big table right, star join, many-to-many wide column, the same with enable_lazy_columns_replication = 0; repeat=5; two value probes (10-codec-columns, 10-codec-parts) read back the codecs time differences above noise level (the big tables are created in 00-data.sql with CODEC(LZ4) on every column, about 40 s of data load per version)

Every probe succeeds on 26.10 (tools/hol run stops at the first exception). Failures on older versions are the result, shown as ✗ Code N (1 UNSUPPORTED_METHOD, 48 NOT_IMPLEMENTED, 62 SYNTAX_ERROR, 115 UNKNOWN_SETTING, 241 MEMORY_LIMIT_EXCEEDED, 403 INVALID_JOIN_ON_EXPRESSION).

What changed between versions

Written only from RESULTS.md (run on 2026-11-05, 12 CPUs, 15.6 GiB Docker VM; no other containers during the 24.8, 25.3 and 26.10 runs, a few idle cap-final-* containers of another task during 25.8, 26.3 and 26.8, so read times only for large gaps).

  • Non-equi ON. On 24.8.14.39 every non-equi form fails with Code 403 unless allow_experimental_join_condition = 1 is set (03-equi-ineq-inner-flag runs, 03-equi-ineq-inner does not). From 25.3.14.14 the range, arbitrary INNER and equality-plus-inequality forms run without the flag. The LEFT join with an arbitrary expression (03-arbitrary-left) still fails with Code 403 on 25.3 through 26.8.36.3, with or without the flag, and runs only on 26.10.3.7.
  • Range joins. On 26.10.3.7 03-range-inner is logged as IE_JOIN; ie_join is in the default join_algorithm list of 26.8.36.3 and 26.10.3.7 and not in that of 25.3 to 26.3. read_rows of the 03 probes is 1,112,053 or 5,000,100 depending on version and probe (25.8.33.6 reads 1,112,053 for the arbitrary INNER join, which is not an IE join), so the difference is not attributed to IE join here.
  • Correlated subqueries. EXISTS and NOT EXISTS fail with Code 1 on 24.8 and 25.3 and run from 25.8.33.6 (where allow_experimental_correlated_subqueries exists, default 1). The correlated scalar subquery in the select list fails with Code 48 on 25.8, 26.3 and 26.8 and runs on 26.10.
  • Runtime filters. enable_join_runtime_filters exists from 26.3.62.3 (default 1). The setting does not change read_rows; it changes how many rows reach the join: JoinProbeTableRowCount of 05-star-on / 05-star-off is 274,366 / 5,500,000 on 26.8.36.3 and 26.10.3.7 and 49,760 / 524,881 on 26.3.62.3. The EXPLAIN of 09-explain-runtime-filter on 26.10.3.7 shows Runtime filters: RF2(customer_id, id) on the facts scan.
  • Star join build side. 05-star-default on 26.3.62.3 builds the hash table from facts: JoinBuildTableRowCount is 5,000,001 and peak memory 224 MiB; on 26.8.36.3 and 26.10.3.7 it builds from 24,882 rows (3 MiB). On 25.3 and 25.8 the build side is 500,001 rows.
  • Join side and memory. With the big table written on the right (02-big-right-default), 24.8.14.39 peaks at 185 MiB; 25.3.14.14 peaks at 77 MiB and 25.8 to 26.10 at 29 to 46 MiB. query_plan_join_swap_table = 'false' brings back 130 to 192 MiB on 25.3 to 26.10 (the setting does not exist on 24.8: Code 115).
  • Memory cap and spilling (06-memory-cap.sql, errors/01). The build side is the 5M-row customers_big with its wide comment; the cap is max_memory_usage = 800000000 (763 MiB). Uncapped peaks, MiB: default 1662 to 1925 (2.2 to 2.5 times the cap), hash 1579 to 1815 (2.1 to 2.4 times), grace_hash with one bucket 1788 to 2231 (2.3 to 2.9 times), partial_merge 987 to 1009 (1.3 times). Under the cap, the default, hash, partial_merge and one-bucket grace_hash all fail with Code 241 on all six versions (errors/01-memory-cap-defaults.sql); writing out max_bytes_ratio_before_external_join = 0.5 gives Code 115 before 26.8 and Code 241 on 26.8 and 26.10. These paths finish: grace_hash with 16 buckets (277 to 305 MiB, 36 to 40 percent of the cap) and with 8 buckets (363 to 452 MiB, 48 to 59 percent) on all six versions, and the default with max_bytes_before_external_join = 200000000 (406 to 422 MiB, 53 to 55 percent of the cap) on 26.8.36.3 and 26.10.3.7 only (Code 115 before: the setting does not exist). On 26.10 the spill shows in ProfileEvents (ExternalProcessingFilesTotal 64, JoinSpillingHashJoinSwitchedToGraceJoin 1).
  • LATERAL forms (errors/02). The comma form and CROSS JOIN LATERAL give Code 62 on all six; a LATERAL subquery that does not reference the left side and LIMIT ... WITH TIES inside LATERAL give Code 62 on 24.8 to 26.8 and Code 48 on 26.10.3.7.
  • Time (10-scale.sql, 5 runs, median (min) in seconds). One machine (12 CPUs), run on 2026-11-05. The 25.8, 26.3 and 26.8 builds ran next to idle cap-final-* containers of another task (22 to 56 percent of 1200% CPU in total at those versions' starts, listed in RESULTS.md), so read only large gaps.

The clear gaps: the big table on the right takes 1.16 to 1.23 s and 1877 MiB on 24.8 against at most 0.22 s and 583 MiB elsewhere; the star join on 26.3 peaks at 2800 MiB (0.32 s) and on 26.8 and 26.10 at 37 to 43 MiB (0.05 s). For 10-many-to-many-wide, 24.8 peaks at 619 MiB and 25.3 to 26.10 at 1429 to 1670 MiB. Its time is 0.30 to 0.62 s on all six builds: 26.8 (0.30 s, min 0.29) and 26.10 (0.38 s, min 0.32) are not slower than 24.8 (0.47 s, min 0.43); only 25.3 (0.62 s, min 0.57) is above it. The run of 2026-11-04, with other containers running, had shown 26.8 and 26.10 at 1.4 to 2 times 24.8; that gap does not reproduce. Turning lazy replication off changes the time by 0.03 s or less on 26.3, 26.8 and 26.10; memory is 28 to 64 MiB lower (1369 to 1478 MiB against 1429 to 1520 MiB). - Codec pin. From 26.9 a merged part of 100 MiB or more defaults to ZSTD(3) (ClickHouse#108786); older builds use LZ4. 00-data.sql pins CODEC(LZ4) on every column of the three big tables, so the timings compare builds, not codecs. The two value probes read it back: 10-codec-columns shows CODEC(LZ4) on all 10 columns on every build, and 10-codec-parts shows part default codecs ['LZ4'] on 24.8 to 26.8 and ['LZ4','ZSTD(3)'] on 26.10 (11 parts, the largest 654130557 bytes). So on 26.10 merged parts did get a ZSTD(3) default during the run, and the pin is what kept the columns LZ4. Builds before 26.9 store LZ4 either way. - Syntax. NATURAL JOIN parses from 26.8.36.3 (Code 62 before); LEFT JOIN LATERAL only on 26.10.3.7 (with allow_experimental_lateral_join = 1). ASOF, SEMI, ANTI, PASTE, USING and FULL with join_use_nulls parse on all six. - Lazy replication. enable_lazy_columns_replication exists from 26.3.62.3 (default 1). Peak memory of 07-lazy-on / 07-lazy-off: 328 / 328 MiB on 26.3, 63 / 136 MiB on 26.8, 65 / 119 MiB on 26.10. - join_algorithm default. default on 24.8.14.39; direct,parallel_hash,hash on 25.3 to 26.3; direct,parallel_hash,hash,ie_join on 26.8 and 26.10. used_join_algorithms is logged only on 26.10.3.7; for the older builds RESULTS.md lists the join processors found in EXPLAIN PIPELINE, which is not an algorithm name.

Not examined: distributed or replicated joins, other table engines (Join, Dictionary), other data sizes, the full_sorting_merge algorithm.

errors/

errors/NN-*.sql follow the same probe rules but tools/hol does not run them (it globs only the top level): they hold results that are failures on 26.10 itself. run_matrix.py runs them after the top-level files and RESULTS.md has a section for each. errors/01-memory-cap-defaults.sql runs the 06 join under the same cap on the paths that do not spill (default, ratio written out, hash, partial_merge, one-bucket grace_hash); errors/02-lateral-forms.sql has the LATERAL forms that do not parse or are not implemented.

Verified

Verified on 24.8.14.39, 25.3.14.14, 25.8.33.6, 26.3.62.3, 26.8.36.3 and 26.10.3.7, 2026-11-05 (./run_matrix.py, all six; tools/hol run on 26.10.3.7).

같은 JOIN SQL을 ClickHouse 여섯 빌드(LTS 24.8, 25.3, 25.8, 26.3, 26.8과 최신 stable 26.10)에서 실행합니다. 프로브·버전마다 실행 여부(또는 오류 코드), 시간, 최대 메모리, 읽은 행 수, JOIN 알고리즘을 기록합니다. 변경 로그에서 가져온 값은 없습니다. RESULTS.md의 모든 셀은 실행 결과이고, 프로브별 원자료(query_log 행, ProfileEvents, 결과 첫 행)는 results/<version>.json에 있습니다.

실행

cd workload/join-across-versions
./run_matrix.py                      # 여섯 버전 전부, 한가한 머신에서 약 4분(2026-11-05). 이미지를 받지 않으므로 미리 있어야 함
./run_matrix.py --versions 26.10     # 한 버전 (versions.txt 줄의 접두사)
./run_matrix.py --only 05            # 파일 또는 프로브 id 접두사. 결과는 JSON에 병합
./run_matrix.py --report-only        # results/*.json에서 RESULTS.md 재생성
tools/hol run workload/join-across-versions   # 저장소 루트에서: 26.10에서만 SQL 실행, 예외 없어야 함

versions.txt는 정확한 태그를 오래된 순으로 고정합니다. 러너(Python 3 표준 라이브러리와 Docker CLI)는 tools/hol up처럼 버전마다 컨테이너 하나를 띄우고, 포트는 열지 않으며, NN-*.sql을 모두 실행한 뒤 컨테이너를 지웁니다. 러너는 범용입니다: -- probe: <id> [repeat=N] [show] [events]가 앞에 붙은 문장이 프로브이고 나머지는 준비 문장입니다. 파일의 -- settings: a, b는 system.settings에서 조회할 설정 목록입니다. 문장은 줄 끝의 ;로 끝나며, 문자열 리터럴 안에서 줄이 ;로 끝나면 안 됩니다. 문장마다 별도 clickhouse-client 호출이므로 SQL에는 단독 SET이 없고 설정은 각 문장의 SETTINGS에 있습니다.

버전 간 변화

RESULTS.md만으로 작성했습니다(2026-11-05 실행, CPU 12개, Docker VM 15.6 GiB). 24.8, 25.3, 26.10 실행 중에는 다른 컨테이너가 없었고 25.8, 26.3, 26.8 실행 중에는 다른 작업의 유휴 cap-final-* 컨테이너가 떠 있었으므로 시간은 큰 차이만 보십시오.

  • 비동등 ON. 24.8.14.39에서는 allow_experimental_join_condition = 1이 없으면 모든 비동등 형태가 Code 403으로 실패합니다 (03-equi-ineq-inner-flag는 실행되고 03-equi-ineq-inner는 안 됩니다). 25.3.14.14부터 범위, 임의 식 INNER, 동등+부등 형태는 플래그 없이 실행됩니다. 임의 식 LEFT JOIN(03-arbitrary-left)은 25.3부터 26.8.36.3까지 플래그 유무와 상관없이 Code 403이고 26.10.3.7에서만 실행됩니다.
  • 범위 조인. 26.10.3.7에서 03-range-inner는 IE_JOIN으로 기록됩니다. 기본 join_algorithm 목록에 ie_join이 있는 것은 26.8.36.3과 26.10.3.7이고 25.3~26.3에는 없습니다. 03 프로브의 read_rows는 버전과 프로브에 따라 1,112,053 또는 5,000,100이어서(25.8.33.6은 IE join이 아닌 임의 식 INNER 조인에서도 1,112,053), 이 차이를 IE join 때문이라고 보지 않습니다.
  • 상관 서브쿼리. EXISTS, NOT EXISTS는 24.8과 25.3에서 Code 1로 실패하고 25.8.33.6부터 실행됩니다(allow_experimental_correlated_subqueries가 있고 기본값 1). select 목록의 상관 스칼라 서브쿼리는 25.8, 26.3, 26.8에서 Code 48이고 26.10에서 실행됩니다.
  • 런타임 필터. enable_join_runtime_filters는 26.3.62.3부터 있습니다(기본 1). 이 설정은 read_rows를 바꾸지 않고 조인에 들어오는 행 수를 바꿉니다: 05-star-on / 05-star-off의 JoinProbeTableRowCount는 26.8.36.3과 26.10.3.7에서 274,366 / 5,500,000, 26.3.62.3에서 49,760 / 524,881입니다. 26.10.3.7의 09-explain-runtime-filter EXPLAIN에는 facts 스캔에 Runtime filters: RF2(customer_id, id)가 보입니다.
  • 스타 조인 빌드 쪽. 26.3.62.3의 05-star-default는 facts로 해시 테이블을 만듭니다: JoinBuildTableRowCount 5,000,001, 최대 메모리 224 MiB. 26.8.36.3과 26.10.3.7은 24,882행(3 MiB)으로 만듭니다. 25.3과 25.8의 빌드 쪽은 500,001행입니다.
  • 조인 쪽과 메모리. 큰 테이블을 오른쪽에 쓰면(02-big-right-default) 24.8.14.39는 최대 185 MiB, 25.3.14.14는 77 MiB, 25.8~26.10은 29~46 MiB입니다. query_plan_join_swap_table = 'false'로 끄면 25.3~26.10에서 130~192 MiB로 돌아갑니다(24.8에는 설정이 없어 Code 115).
  • 메모리 상한과 스필(06-memory-cap.sql, errors/01). 빌드 쪽은 넓은 comment가 있는 500만 행 customers_big이고 상한은 max_memory_usage = 800000000(763 MiB)입니다. 무제한 최대치(MiB): 기본 1662~1925(상한의 2.2~2.5배), hash 1579~1815(2.1~2.4배), 버킷 1개 grace_hash 1788~2231(2.3~2.9배), partial_merge 987~1009(1.3배). 상한 아래에서 기본, hash, partial_merge, 버킷 1개 grace_hash는 여섯 버전 모두 Code 241로 실패합니다(errors/01-memory-cap-defaults.sql). max_bytes_ratio_before_external_join = 0.5를 명시하면 26.8 이전은 Code 115, 26.8과 26.10은 Code 241입니다. 끝나는 경로: 버킷 16개 grace_hash(277~305 MiB, 상한의 36~40%)와 버킷 8개(363~452 MiB, 48~59%)는 여섯 버전 모두, max_bytes_before_external_join = 200000000을 둔 기본값(406~422 MiB, 상한의 53~55%)은 26.8.36.3과 26.10.3.7에서만(이전은 설정이 없어 Code 115). 26.10의 ProfileEvents에 스필이 보입니다(ExternalProcessingFilesTotal 64, JoinSpillingHashJoinSwitchedToGraceJoin 1).
