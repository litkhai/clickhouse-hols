Indexes across ClickHouse versions

The same index SQL run on six builds (the LTS lines 24.8, 25.3, 25.8, 26.3, 26.8 and the latest stable 26.10). The main measure is how much each query reads: the granules that EXPLAIN indexes = 1 selects and read_rows from system.query_log. Times are recorded only for the 20M-row tables, as the minimum of 5 runs. Every cell in RESULTS.md comes from a run; the raw per-probe data (including query_log rows) is in results/<version>.json.

What is probed: the primary index (a condition on the first sorting-key column, on the second column only, on a function of the key, on a non-key column, use_primary_key = 0); skip indexes on non-key columns (minmax on a correlated and an uncorrelated column, set(100) vs set(0), bloom_filter with GRANULARITY 1 and 4, tokenbf_v1 at two sizes, ngrambf_v1, !=, NOT, OR, a value-preserving cast); the text index (hasToken, hasAnyTokens, hasAllTokens, LIKE, =, NOT, direct read, index size and posting-list codec); automatic minmax indices; the query condition cache; a skip index under FINAL; index sizes; and the statements each build rejects.

Run it

cd workload/index-across-versions
./run_matrix.py                      # all six versions, about 20 minutes; pulls nothing, images must exist
./run_matrix.py --versions 26.10     # one version (prefix of a line in versions.txt)
./run_matrix.py --only 03            # one file or probe-id prefix (a file's results replace that file in the JSON)
./run_matrix.py --report-only        # rebuild RESULTS.md from results/*.json
tools/hol run workload/index-across-versions   # from the repository root: the SQL on 26.10 only, must not raise

versions.txt pins the exact tags, oldest first. run_matrix.py is the same file as in workload/final-across-versions, workload/join-across-versions and workload/upsert-across-versions; it removes each container with docker rm -f -v. Containers are named iav-<tag>. A statement preceded by -- probe: <id> [repeat=N] [show] [value] is a probe, the others are setup; value puts the first result row in the table cell, show prints the newest version's rows. -- settings: a, b lists settings to look up in system.settings (then system.merge_tree_settings). Each statement runs in its own clickhouse-client call, so there is no bare SET. Each probe's comment states the correct answer computed from the data. A setup statement that fails skips the rest of its file, so statements that only newer builds accept sit at the end of a file.

Granules come from a probe named <id>-g that keeps the PrimaryKey, Skip, Name:, Granules: and Search Algorithm: lines of EXPLAIN indexes = 1 for the same query (26.8 and 26.10 draw the plan as a tree, so the probe strips the │ └ ├ ─ prefixes first).

Tables of 1M rows or more carry CODEC(LZ4) on every column: from 26.9 a part of 100 MiB or more defaults to ZSTD(3) (ClickHouse#108786), older builds write LZ4, so without the pin the sizes and times would compare codecs as well as builds. 07-codec shows the part default and the column codec on each build.

What the runs show

Run 2026-11-05 on one 12-CPU, 15.6 GiB Docker VM, a fresh container per build. Another session's containers (lf-gateway-lab-*) were running at 0–100% of 1,200% CPU when each build's run started (table in RESULTS.md). Granules are selected/total from EXPLAIN indexes = 1; rows are read_rows.

Primary index — the same on all six builds. On ORDER BY (a, b) with 1,000 granules: a = 3 selects 101, a AND b 1, a IN (3, 7) 202. A condition on b alone selects 19 when a has 10 values and 1,000 when it has 100,000 (generic exclusion search; the Search Algorithm: line appears from the 25.8 build). On ORDER BY ts: a one-day range and toDate(ts) = … both 12, toHour(ts) = 3 231 (not all: the function is monotonic within a granule's range, so granules whose range cannot contain hour 3 are excluded), a non-key column 1,000. use_primary_key = 0 exists from the 26.3 build and selects 1,000. count() with a key condition read only the boundary granules on every build (16,385 rows for 819,200 matching).

  • On 26.8 and 26.10 the set probes read 0 rows for a different reason: EXPLAIN shows a Statistics step (Granules: 0/1000) before PrimaryKey. Column statistics are built automatically (auto_statistics_types basic, uniq_v2; system.settings_changes lists the default from 26.4, as is use_statistics_for_part_pruning = 1), and the value 100001 is outside the column's range, so the whole part is skipped. The 26.3 build reads all 1,000 granules. The set(100) result on ≤26.3 is the one the index itself gives: a granule with more distinct values than the limit cannot be skipped. set(0) (no limit) works but its index is 30.1 MiB against 67 bytes.
  • toNullable(uid) = … uses the index from the 26.8 build: ClickHouse#123239 (26.10), backported to 26.8 as #123727.
  • OR across two indexes is <Combined skip indexes> from the 26.3 build (25.12 changelog, use_skip_indexes_for_disjunctions); 25.8 reads all 8,192,000 rows.
  • tokenbf_v1 does not serve LIKE '%word%'; ngrambf_v1 does, down to n characters. With the parameters (1024, 2, 0) the token filter kept 825 of 1,000 granules (too small for ~9,000 tokens per granule).
  • Index sizes on 24.8–26.8: i_tok 25.7 MiB, i_ngr 26.3 MiB, i_uid 7.8 MiB, i_tok_small 0.81 MiB; 26.10 16.6, 15.6, 7.6 and 0.51 MiB. The columns are pinned to CODEC(LZ4), but the index files take the part's default codec, which is ZSTD(3) on 26.10 for this 440 MiB part.

text index (26.3+; 20,000,000 rows, 2,442 granules). Default granularity 100,000,000 (one index block per part). hasToken, hasAnyTokens, hasAllTokens select 20 granules (163,840 rows); msg = … 1; NOT hasToken all. count() with hasToken is answered from the index on 26.8 and 26.10 (16 and 0 bytes read; 26.10 still reports read_rows 20,000,000). LIKE '%timeout%' and LIKE '%imeou%': 26.3 reads all 2,442 granules (975,578,100 bytes, 31 ms), 26.8 and 26.10 select 20 (4–5 ms) — the 26.4 changelog has "LIKE queries … can use text indices" (#98149). Without the index (use_skip_indexes = 0) the same lookup takes 25–31 ms, with it 1–2 ms. Size: the default index was 233.3 MiB (26.3, 26.8) and 232.9 MiB (26.10) against a 225.4 MiB data part; posting_list_codec = 'bitpacking' 87.5 MiB (26.3), 97.6 MiB (26.8), 97.2 MiB (26.10); 'pfor' 40.0 MiB (26.10 only; 26.8 rejects it with Code 36).

Index type names per build (errors/): inverted is refused on 24.8 and 25.3 (Code 127, "use full_text"); full_text is accepted on 25.3 with allow_experimental_full_text_index = 1 in the CREATE's SETTINGS, on 24.8 only after a session SET (checked by hand); 25.8 accepts text(tokenizer = 'default') (experimental); from 26.3 text needs a tokenizer (Code 36) and 'default' is unknown. MergeTree without ORDER BY is refused on ≤25.8 (Code 42) and accepted from 26.3 (create_table_empty_primary_key_by_default, 25.11). force_primary_key and force_data_skipping_indices refuse with Code 277 on every build.

Automatic minmax indices (25.3+). add_minmax_index_for_numeric_columns = 1 and …_string_columns = 1 create auto_minmax_index_id, …_s, …_v: a range on the correlated UInt32 selects 2 of 1,000 granules (1,000 without), the String 1. A DateTime range is not covered (1,000) until add_minmax_index_for_temporal_columns = 1 (from the 26.3 build): 12. 24.8 does not know the settings (Code 115).

Query condition cache. The second run of a selective filter on a non-key column read 262,144 rows instead of 8,192,000 from the 25.8 build (default on; 25.4 changelog). 25.3 has the setting with default 0; with = 1 the second run read 196,608. After an INSERT of 1,000 matching rows the count was right (1,004) and 263,144 rows were read. A lightweight UPDATE between two runs gave 4 then 5, correct, on every build that has UPDATE (25.8+). At 20M rows the cache made a repeated lookup without any index as cheap as with one (below).

Skip index under FINAL. 24.8 and 25.3 do not use the index under FINAL by default (1,210,112 rows read); from 25.8 they do (171,072), and EXPLAIN adds a PrimaryKeyExpand step (5 → 14 granules, the same key ranges in the other part). Answers are correct on every build. With use_skip_indexes_if_final = 0, ≤26.3 read 1,210,112 rows in both runs of the matrix; 26.8 and 26.10 read fewer and the number differed between the two runs (1,137,344–1,191,920). Not the cache (the same with it off, by hand on 26.10); not investigated further.

20M-row lookups (07-scale.sql)

Minimum of 5 runs in ms (durations_ms in results/*.json), use_query_condition_cache = 0 (24.8 has no cache; its cell is the run without the setting). All columns CODEC(LZ4).

Query 24.8 25.3 25.8 26.3 26.8 26.10 26.10, table default LZ4
primary key id = … 1 1 1 2 1 1
bloom_filter uid = … (475,136 rows) 4 5 4 5 5 18 5
same, use_skip_indexes = 0 (20M rows) 5 7 6 5 6 5
tokenbf_v1 hasToken (163,840 rows) 38 40 38 35 37 67 37
same, use_skip_indexes = 0 45 43 32 29 25 23
non-key column, no index 4 4 4 4 4 4
  • 26.10's slower index lookups are the index files' codec: the part default is ZSTD(3) (07-codec), so the tokenbf index is 40.6 MiB instead of 62.9 MiB and slower to read. Pinning the table's default_compression_codec = 'LZ4' (big_lz4, the table setting exists from the 25.8 build) gives 37 and 5 ms.
  • A bloom_filter on a 64-bit hash saved nothing here: 4–5 ms with it, 5–7 ms without. The tokenbf on a string column was slower than scanning it on 25.8–26.10 (35–38 ms against 23–32 ms): reading 63 MiB of filter costs more than the scan it avoids. The text index (03-text.sql) answered the same lookup in 1–2 ms.
  • With the cache on (the default from 25.8), a repeated lookup with no index took 1–3 ms (65,536 / 327,680 rows).

Not covered here

  • Distributed and replicated tables, SharedMergeTree, parallel replicas, ClickHouse Cloud.
  • Projections, vector_similarity indexes, column statistics as a query-planning input (only their part pruning showed up), tokenizers other than splitByNonAlpha (see usecase/fulltext-search and usecase/korean-rag-tokenizers), phrase search, data larger than 20M rows, many parts per table.

같은 인덱스 SQL을 빌드 여섯 개(LTS 24.8, 25.3, 25.8, 26.3, 26.8과 최신 안정판 26.10)에서 실행합니다. 주된 척도는 쿼리마다 읽는 양입니다. EXPLAIN indexes = 1이 고른 granule 수와 system.query_log의 read_rows입니다. 시간은 2,000만 행 테이블에서만 5회 최솟값으로 기록합니다. RESULTS.md의 모든 셀은 실행 결과이고, probe별 원자료 (query_log 행 포함)는 results/<버전>.json에 있습니다.

확인하는 것: 기본 인덱스(정렬 키 첫 컬럼 조건, 둘째 컬럼만의 조건, 키의 함수, 키가 아닌 컬럼, use_primary_key = 0), 키가 아닌 컬럼의 skip index(상관 있는 컬럼과 없는 컬럼의 minmax, set(100)과 set(0), GRANULARITY 1 · 4의 bloom_filter, 크기 두 가지의 tokenbf_v1, ngrambf_v1, !=, NOT, OR, 값을 바꾸지 않는 캐스트), text 인덱스 (hasToken, hasAnyTokens, hasAllTokens, LIKE, =, NOT, direct read, 인덱스 크기와 posting list 코덱), 자동 minmax 인덱스, query condition cache, FINAL 아래의 skip index, 인덱스 크기, 빌드마다 거부되는 문장.

실행

cd workload/index-across-versions
./run_matrix.py                      # 여섯 버전 전부, 약 20분; 이미지를 받지 않으므로 미리 있어야 함
./run_matrix.py --versions 26.10     # 한 버전(versions.txt 줄의 접두사)
./run_matrix.py --only 03            # 파일이나 probe id 접두사 하나(그 파일의 결과만 JSON에서 바뀜)
./run_matrix.py --report-only        # results/*.json에서 RESULTS.md만 다시 만듦
tools/hol run workload/index-across-versions   # 저장소 루트에서: 26.10에서만 SQL 실행, 오류가 없어야 함

versions.txt는 정확한 태그를 오래된 순으로 고정합니다. run_matrix.py는 workload/final-across-versions, workload/join-across-versions, workload/upsert-across-versions와 같은 파일이고, 컨테이너를 docker rm -f -v로 지웁니다. 컨테이너 이름은 iav-<태그>입니다. -- probe: <id> [repeat=N] [show] [value] 바로 뒤의 문장이 probe이고 나머지는 준비 문장입니다. value는 결과 첫 행을 표 셀에, show는 최신 버전의 결과 행을 출력합니다. -- settings: a, b는 system.settings(없으면 system.merge_tree_settings)에서 찾을 설정입니다. 문장마다 clickhouse-client를 따로 부르므로 단독 SET은 쓰지 않습니다. probe 주석에는 데이터로 계산한 정답이 있습니다. 준비 문장이 실패하면 그 파일의 나머지가 건너뛰어지므로, 새 빌드만 받는 문장은 파일 끝에 둡니다.

granule 수는 같은 쿼리의 EXPLAIN indexes = 1에서 PrimaryKey, Skip, Name:, Granules:, Search Algorithm: 줄만 남기는 <id>-g probe가 냅니다(26.8 · 26.10은 계획을 트리로 그려서 │ └ ├ ─ 접두사를 먼저 지움).

결과

2026-11-05, 12 CPU · 15.6 GiB Docker VM 한 대에서 빌드마다 새 컨테이너로 실행했습니다. 다른 세션의 컨테이너 (lf-gateway-lab-*)가 각 빌드 실행 시작 시점에 1,200% 중 0–100% CPU로 돌고 있었습니다(RESULTS.md 표). granule은 EXPLAIN indexes = 1의 고른 수/전체, 행은 read_rows입니다.

기본 인덱스 — 여섯 빌드 모두 같음. granule 1,000개의 ORDER BY (a, b)에서 a = 3은 101, a AND b는 1, a IN (3, 7)은 202개를 고릅니다. b만의 조건은 a가 값 10개일 때 19, 값 100,000개일 때 1,000입니다(generic exclusion search; Search Algorithm: 줄은 25.8 빌드부터 나옴). ORDER BY ts에서 하루 범위와 toDate(ts) = …는 둘 다 12, toHour(ts) = 3은 231입니다(전부가 아님: 함수가 granule 범위 안에서는 단조라, 3시를 담을 수 없는 granule은 제외됨). 키가 아닌 컬럼은 1,000입니다. use_primary_key = 0은 26.3 빌드부터 있고 1,000을 고릅니다. 키 조건이 있는 count()는 모든 빌드에서 경계 granule만 읽었습니다(일치 819,200행에 16,385행).

빌드별 인덱스 타입 이름(errors/): inverted는 24.8 · 25.3에서 거부(Code 127, "full_text를 쓰라"). full_text는 25.3에서 CREATE의 SETTINGS에 allow_experimental_full_text_index = 1을 주면 되고, 24.8은 세션 SET 뒤에만 됩니다 (손으로 확인). 25.8은 text(tokenizer = 'default')(실험 기능)를 받습니다. 26.3부터 text에는 토크나이저가 필요하고 (Code 36) 'default'는 알 수 없는 토크나이저입니다. ORDER BY 없는 MergeTree는 ≤25.8에서 거부(Code 42), 26.3부터 허용(create_table_empty_primary_key_by_default, 25.11). force_primary_key · force_data_skipping_indices는 모든 빌드에서 Code 277로 거부합니다.

자동 minmax 인덱스(25.3+). add_minmax_index_for_numeric_columns = 1과 …_string_columns = 1은 auto_minmax_index_id, …_s, …_v를 만듭니다. 상관 있는 UInt32 범위가 granule 1,000개 중 2개(설정 없으면 1,000), String은 1개입니다.
