Case study: a telco OSS data lake — architecture, use cases, what a PoC verified

A telco OSS (operations: equipment, faults, quality; not BSS, which is billing) collects logs, metrics and events from every device on the network (UE: phones, IoT modules, vehicles, routers) and from the network equipment itself. This lab shows who uses that data, and how: a reference architecture for a typical telco OSS lake, the use cases built on it (NOC map, dashboards, ad hoc analysis, request/response serving, subscriptions, bulk export, schema contracts, data quality, pipeline observability, lake history, AI agents, Managed Postgres as an expansion), and a small ClickHouse lake that actually runs five of them.

It is made to be shown to colleagues as a case study: situation → the industry trend (virtualizing the OSS data layer, from public sources) → architecture → use cases → features verified in the PoC → lessons → try it, with next steps. A static page in English (default, at /), Korean, Japanese and Chinese works without ClickHouse; a local live demo has a "send next minute" button. Dark only, with the colours of clickhouse.com (computed styles, read 2026-10-18).

A composite scenario: a fictional operator and fictional cities, built from common telco OSS practice (medallion layering over 3GPP-style data). The lab runs device (UE) traces only; performance counters (PM), alarms (FM) and complaints (VoC) appear as sources in the figure, not as tables. Names are invented and figures are measured in this lab on generated data at reduced scale (180,000 rows a minute, three cities, about 20,000 grid cells, far below a real operator's trace intake). The cities sit in open ocean, so no coordinate points to a real place. IMSIs use the test network code 001-01. Measurements use LTE terms (RSRP/RSRQ/SINR, TS 36.214); each one's location is assumed to come from MDT (TS 37.320) location reports or positioning, mapped to an H3 res-9 grid cell (about 0.1 km²). A grid cell is a location bucket, not a radio cell or sector.

Verified on ClickHouse 26.9.13.15 (clickhouse/clickhouse-server:26.9.13.15), 2026-10-18: tools/hol run usecase/oss-network-quality-lake passes (01–05 and 99, about 30 s; two runs in a row after the last change), and the live demo was run with ui/up.sh and its button pressed several times. Machine: Apple M4 Pro, macOS, Docker Desktop; the container sees 12 CPUs and 7.75 GiB.

Reference architecture

Sources (devices, base stations, servers, applications) → collection (an agent per node, an aggregator) → raw messages on a message bus (Kafka) → stream processing that maps to an industry information model and enriches → curated messages → sink → storage: history in an open-table-format lake, ready-to-use summaries (gold) in ClickHouse → serving in three ways (request/response over HTTP, bulk export, subscription) → NOC screens, dashboards, analysts, business apps, AI agents. Two rails run along it: a schema contract in Git from which every stage's schema and DDL is generated, and a control-plane API that declares, deploys and observes every component.

Every minute the generator injects a 22 dB drop into one res-7 area (about 49 grid cells), so the alert use case and the live feed have something new to carry each minute. That shows pipeline latency, not detection quality: the rule (12 dB below the previous 59 minutes, folded per res-7 area) is built to find exactly what is injected. Real rules also watch measurement counts collapsing, persistence over several minutes and recent configuration changes.

Coverage comes from distance to the serving site (one per res-8 area downtown, one per res-7 area further out), a fixed offset per site and per city, and a little extra loss with distance from the centre, so the three cities differ. Known coverage gaps (known_weak in the inventory) are left out of the "weakest 10" so that newly weak places show. PCI is fixed per serving site.

Features verified in the PoC

Ingest as received · cleaning at insert time (MV) · enrichment from an inventory dictionary (dictGet, district names) · pre-aggregation at insert (cell × 1 min) · gold on gold (cell × 10 min cascading from cell × 1 min, equal to raw) · a geography axis (district × 1 min) · an answer refreshed every minute (refreshable MV) · the same 20 rows from every stage · sudden-drop alerts · HTTP serving with a read-only user · H3 geo functions. Each has a check in 03–05, except "20 rows readable during refreshes" and "the read-only user cannot write", which were checked by hand on 2026-10-18.

Lessons (a–c measured 2026-10-18 on this lab, 26.9.13.15; d–f are practice, not measured)

  • Nullable costs mostly in query complexity: the NOC query on bronze needs assumeNotNull, IS NOT NULL, stringToH3, cityHash64; on silver it does not.
  • A uniq state is sized by distinct values per group, not by input type: 300 distinct values give 1,203 B for String and for UInt64 alike; uniqCombined(12) is 2,651 B at 300 and at 1,000, where uniq is 4,003 B. In the lab the 1-minute rollup holds 2.43 M states of 34 B on average, the 10-minute one 264 K of 193 B: choose the grain where user counts live.
  • Build coarse rollups from fine ones (cascading MV on the 1-minute table, uniqMergeState + sums); not a refreshable MV with APPEND, which by design double-inserts when its window is wider than its interval (reasoned, not reproduced here).
  • A time column named for local time but typed UTC shifts buckets and TTL by the UTC offset; store instants with an explicit time zone.
  • Many consumers (dashboards, an AI agent over MCP, a catalogue, Kafka Connect batches) need their own users and limits: read-only users with result and time limits, larger batches or async inserts.
  • A pseudonymous trace is still personal data (see "Subscriber data" below).

Subscriber data

Bronze holds a vendor-supplied hash of the IMSI. Here it is an unkeyed SHA-256 of a test PLMN plus a 10-digit MSIN, which can be reversed by trying every number in that range: a real deployment must not rely on an unkeyed hash. Silver replaces it with cityHash64, a stable 64-bit pseudonym, not anonymous data: a grid cell, a millisecond timestamp and a fixed hash per row are enough to rebuild one subscriber's movements, and a cell-minute's users can be 1. Pseudonymised data stays personal data (GDPR Recital 26, Art. 4(5)). In production: hash with a key held outside the lake (HMAC) and rotate it, keep the row-level stages narrow and short-lived, and hide counts below a minimum in served results.

The layers this lab runs

In the reference architecture raw messages and standardization live in Kafka and stream processing. To keep the flow visible in one place, this lab keeps all four stages inside ClickHouse and links them with materialized views. All four are tables in database oss_lake (Atomic).

Same answer from every layer

03-queries.sql asks the NOC question of each layer through four views (noc_from_bronze, _silver, _gold, _serving), refreshes serving, and fails unless all four return the same 20 rows (serving is frozen into a Memory table first, because the scheduled refresh may swap it during the checks). The check was seen to fire: changing one serving row by hand made it stop with bronze differs from serving, and it caught the wrong-result bug described below (silver differs from serving).

A wrong result met on the way (26.6–26.9)

Two early tools/hol runs failed the same-20-rows check: silver returned a few rows fewer than bronze for the same hour. Cause, measured 2026-10-18: for a DateTime64(3) primary-key column, the condition event_ts < <a DateTime value> becomes the key condition event_ts <= <that value> - 1 s (EXPLAIN indexes = 1 shows event_ts in (-Inf, 1792313039] for < '2026-10-18 08:44:00'). A granule that starts inside the last second (here at 08:43:59.003, 3,033 rows) is skipped, so its rows vanish from WHERE while countIf with the same condition still counts them. It depends on where granule boundaries fall, which is why it came and went between runs.

A minimal reproduction: one DateTime64(3) column, index_granularity = 1000, 5,000 rows 2 ms apart starting 3 ms after a whole second, so that a granule begins inside the last second before the bound; then WHERE ts < toDateTime('… 00:00:09'). It returns 4,000 rows instead of 4,499 on 26.6.8.7, 26.8.22.13 and 26.9.13.15, and the correct count on 25.8.33.6. With rows starting exactly on the second the granules start on the second and the result is correct, which is why a careless repro passes (rechecked 2026-10-18 on 26.9.13.15 in review). Whether it is already reported upstream was not checked.

The lab compares event_ts with a DateTime64(3) bound (toDateTime64(…, 3), the key condition is then (-Inf, '1792313040')), and the run that had shown the bug passed with that change. Gold's bucket is a DateTime compared with a DateTime, so it is not affected.

The one pitfall: an aggregate state that no longer matches its source

An AggregateFunction column's argument type must match the source column, Nullable included. pitfall.sql reproduces it in a scratch database (tools/hol does not run it; it fails on purpose). Measured 2026-10-18:

  • A mismatch the server can see is refused at CREATE: avgState(rsrp) over a Nullable(Float32) into AggregateFunction(avg, Float32) fails with CANNOT_CONVERT_TYPE on 25.8.33.6, 26.6.8.7, 26.8.22.13 and 26.9.13.15.
  • A mismatch that arrives later is not: the source column was Float32, the MV was created, then ALTER TABLE … MODIFY COLUMN rsrp Nullable(Float32) succeeded, and every INSERT after it failed (26.9.13.15):

Code: 70. DB::Exception: Conversion from AggregateFunction(avg, Nullable(Float32)) to AggregateFunction(avg, Float32) is not supported: while converting source column avg_rsrp_st to destination column avg_rsrp_st: while pushing to view oss_pitfall.kpi_mv … (CANNOT_CONVERT_TYPE)

The source row was written anyway (trace 2 rows, kpi 1 row), so the source keeps growing while the aggregate silently stops.

The lab's gold layer avoids it by keeping rsrp as plain sums (count(rsrp), sum(ifNull(rsrp, 0))) and feeding uniqState a non-Nullable hash. Another fix is a state type that follows the source (AggregateFunction(avg, Nullable(Float32))).

On ClickHouse Cloud (live site)

https://oss-lake.clickhouse.kr/ is live data, not a recording:

  • Lake: database oss_lake on a ClickHouse Cloud service on AWS, loaded 2026-10-18 on 26.6.1 by cloud/load.py. That is the same 01–05 files plus the Cloud differences listed in its docstring. All checks in 03–05 passed there.
  • Feed: cloud/feed.sql adds two refreshable MVs. feed_rmv generates the next minute every minute (up to five to catch up after a pause, never a minute twice). anchor_rmv then moves the lake's "now"; the serving refresh depends on it. The TTLs come from 01-schema.sql (bronze and silver 1 day, gold 2 days, whole parts dropped), so a feed that never stops keeps the lake the same size. params (one row a minute) has none, so a long pause cannot empty the lake's clock. feed start restarts the clock one minute ago when it is more than five minutes behind, so the gap is skipped, not replayed. The live demo says "stopped" when no new minute has arrived for three minutes.
  • Site: Vercel project oss-lake. The pages are static. api/index.py serves the demo's GET endpoints as the read-only user oss_reader: readonly = 1, 20 s, 30 M rows read and 200,000-row result limits, an hourly quota (3,000 queries, 5 G rows read), a 20 s edge cache. The edge cache key is the full URL, so the function refuses any query string (400) and redirects a trailing slash (308) without querying ClickHouse. Errors return a fixed body; the detail goes to the function log. It has no write endpoint (POST returns 405). When the function cannot reach ClickHouse or the quota is spent, the demo falls back to the recorded minutes. Pages and function answer with a Content-Security-Policy (default-src 'self', inline scripts and styles allowed, frame-ancestors 'none'), X-Frame-Options: DENY and a Permissions-Policy that turns off camera, microphone, location, payment and USB (vercel.json).

Measured 2026-10-18 on that service (2 replicas, 8 GiB minimum each, 2 vCPUs):

  • Load times: 01 in 9 s, 02 in 66 s, 03 in 15 s, 04 in 2 s, 05 in 12 s.
  • The feed ran with no failed refresh, writing 180,000 rows a minute, and the lake's "now" stayed within the current wall-clock minute.

Found on the way: the inventory dictionary has a copy on each replica. SYSTEM RELOAD DICTIONARY reloaded one replica, the other kept a copy loaded while the inventory was still empty, and every silver row of the history load got an empty district. The 05 check caught it. The loader now reloads ON CLUSTER 'default' and waits until every replica holds the whole inventory. The dictionary also reloads itself every 5–10 minutes (LIFETIME(MIN 300 MAX 600)). District names are written into silver and gold at insert, so after an inventory change: reload on every replica, then reprocess the affected window.

The checks in 05 look at the last complete hour before the lake's "now", not at whole tables, so they still hold days after a load although the layers keep different TTLs. They assume an unbroken hour; right after feed start skipped a gap, wait an hour before rerunning them. The bronze check fails on a whole missing minute as well as on a partial or duplicated one (checked 2026-10-18 by deleting one minute from a local lake: "bronze is missing a minute").

통신사 OSS(운영: 장비, 장애, 품질. 요금·청구를 다루는 BSS가 아님)는 망에 붙은 모든 단말(UE: 휴대폰, IoT 모듈, 차량, 공유기 등)과 망 장비의 로그, 지표, 이벤트를 모읍니다. 이 실습은 그 데이터를 누가 어떻게 쓰는지를 보여 줍니다. 전형적인 통신사 OSS 레이크의 참조 구조, 그 위의 유즈케이스(NOC 지도, 대시보드, 즉석 분석, 즉시 조회 서빙, 구독, 대량 추출, 스키마 계약, 데이터 품질, 파이프라인 관측, 레이크 이력, AI 에이전트, 확장안으로 Managed Postgres), 그리고 그중 다섯 가지를 실제로 돌리는 작은 ClickHouse 레이크입니다.

동료들과 나누는 사례 연구입니다. 상황 → 업계 흐름(OSS 데이터 레이어의 가상화, 공개 자료) → 아키텍처 → 유즈케이스 → PoC에서 검증한 기능 → 배운 것 → 직접 해 보기와 다음 단계 순서입니다. 정적 페이지는 영어(기본, /), 한국어, 일본어, 중국어로 ClickHouse 없이 열리고, 로컬 라이브 데모에는 "다음 1분 보내기" 버튼이 있습니다. 다크 모드 전용이며 clickhouse.com의 색(계산된 스타일, 2026-10-18 확인)을 씁니다.

합성 시나리오입니다. 가상의 통신사와 가상의 도시를 두고, 흔한 통신 OSS 관행(3GPP 형태의 데이터 위에 메달리온 계층)으로 구성했습니다. 실습이 돌리는 것은 단말(UE) 트레이스뿐이고, 성능 카운터(PM)·경보(FM)· 고객 불만(VoC)은 그림 속 원천일 뿐 테이블은 없습니다. 이름은 지어낸 것이고, 수치는 축소한 규모의 생성 데이터(분당 180,000행, 도시 3개, 격자 약 20,000개 — 실제 통신사의 트레이스 유입보다 훨씬 작음)로 이 실습에서 잰 값입니다. 도시는 먼 바다 위에 두어 어떤 좌표도 실제 장소를 가리키지 않습니다. IMSI는 시험망 코드 001-01을 씁니다. 측정은 LTE 용어(RSRP/RSRQ/SINR, TS 36.214)를 쓰고, 측정 위치는 MDT(TS 37.320) 위치 보고나 측위 결과를 H3 res-9 격자(약 0.1 km²)로 바꾼 것으로 가정합니다. 격자는 위치 단위이지 무선 셀이나 섹터가 아닙니다.

참조 구조

원천(단말, 기지국, 서버, 애플리케이션) → 수집(노드마다 에이전트, 집계기) → 메시지 버스(Kafka)의 원천 메시지 → 업계 표준 정보 모델에 맞추고 부가 정보를 붙이는 스트림 처리 → 정제된 메시지 → 싱크 → 저장: 이력은 오픈 테이블 포맷 레이크, 바로 쓰는 요약(골드)은 ClickHouse → 세 가지 서빙(HTTP 즉시 조회, 대량 추출, 구독) → NOC 화면, 대시보드, 분석가, 업무 앱, AI 에이전트. 옆으로 두 줄이 함께 갑니다. 모든 단계의 스키마와 DDL을 만드는 Git의 스키마 계약, 모든 구성 요소를 선언하고 배포하고 관측하는 컨트롤 플레인 API입니다.

생성기는 1분마다 res-7 지역 하나(격자 약 49개)에 22 dB 하락을 넣습니다. 그래서 알림 유즈케이스와 라이브 데모가 매분 새로 실어 나를 것이 생깁니다. 이것은 검출 품질이 아니라 파이프라인 지연을 보여 줍니다. 규칙(직전 59분보다 12 dB 아래, res-7 지역으로 묶음)이 넣은 것을 그대로 찾도록 만들어져 있기 때문입니다. 실제 규칙은 측정 수 급감, 몇 분 이상 지속, 최근 설정 변경도 함께 봅니다.

커버리지는 서빙 사이트(도심은 res-8 지역마다, 바깥은 res-7 지역마다 하나)까지의 거리, 사이트와 도시마다 고정된 오프셋, 도심에서 멀어질수록 조금 더해지는 손실로 정합니다. 그래서 세 도시가 서로 다릅니다. 이미 아는 음영 지역(인벤토리의 known_weak)은 "신호 약한 10"에서 빼서 새로 약해진 곳이 보이게 합니다. PCI는 서빙 사이트마다 고정입니다.

PoC에서 검증한 기능

받은 그대로 적재 · 적재 순간의 정제(MV) · 인벤토리 Dictionary로 보강(dictGet, 지역 이름) · 적재 시 사전 집계(셀 × 1분) · 골드 위의 골드(셀 × 1분에서 이어받는 셀 × 10분, 원본과 일치) · 지리 축(지역 × 1분) · 1분마다 새로 고치는 답(Refreshable MV) · 모든 단계에서 같은 20행 · 급격한 하락 알림 · 읽기 전용 사용자의 HTTP 서빙 · H3 지리 함수. 각각 03–05에 검사가 있고, '새로 고침 중에도 20행'과 '읽기 전용 사용자는 쓰지 못함'은 2026-10-18 손으로 확인했습니다.

배운 것 (a–c는 2026-10-18 이 실습에서 26.9.13.15로 측정, d–f는 실무 지침이며 측정하지 않음)

  • Nullable의 비용은 주로 질의의 복잡도입니다. 브론즈의 NOC 질의에는 assumeNotNull, IS NOT NULL, stringToH3, cityHash64가 필요하고 실버에서는 필요 없습니다.
  • uniq 상태의 크기는 입력 타입이 아니라 그룹당 서로 다른 값의 수가 정합니다. 300개면 String과 UInt64 모두 1,203 B, uniqCombined(12)는 300개와 1,000개 모두 2,651 B(그때 uniq는 4,003 B). 이 실습의 1분 요약은 평균 34 B 상태 243만 개, 10분 요약은 193 B 상태 26.4만 개입니다. 사용자 수를 둘 단위를 고르세요.
  • 거친 요약은 고운 요약에서 만듭니다(1분 테이블에 연쇄 MV, uniqMergeState + 합계). APPEND를 쓴 Refreshable MV는 창이 주기보다 넓으면 설계상 두 번 넣습니다(추론이며 여기서 재현하지 않음).
  • 이름은 현지 시각인데 타입은 UTC인 시간 컬럼은 버킷과 TTL을 UTC와의 시차만큼 밀어 놓습니다. 시각은 시간대를 명시해 저장하세요.
  • 소비자(대시보드, MCP의 AI 에이전트, 카탈로그, Kafka Connect 배치)가 많아지면 각자의 사용자와 한도가 필요합니다. 읽기 전용 사용자에 결과·시간 한도, 적재 쪽은 큰 배치나 async insert.
  • 가명 트레이스도 개인정보입니다(아래 "가입자 데이터").

가입자 데이터

브론즈에는 벤더가 준 IMSI 해시가 들어 있습니다. 여기서는 시험망 PLMN에 10자리 MSIN을 붙인 값의 키 없는 SHA-256이라, 그 범위의 번호를 모두 대입해 보면 되돌릴 수 있습니다. 실제 환경에서는 키 없는 해시에 기대면 안 됩니다. 실버는 이를 cityHash64로 바꾸는데, 이것은 고정된 64비트 가명이지 익명 데이터가 아닙니다. 행마다 격자, 밀리초 시각, 고정 해시가 있으면 가입자 한 명의 이동 경로를 다시 그릴 수 있고, 격자·분 단위 users가 1일 수도 있습니다. 가명처리한 데이터도 개인정보입니다(GDPR 전문 26항, 제4조(5)). 운영에서는 레이크 밖에 둔 키로 해시(HMAC)하고 키를 교체하며, 행 단위 단계는 접근을 좁히고 보존 기간을 짧게 두고, 서빙 결과에서는 최소 인원 미만을 가립니다.

이 실습이 돌리는 레이어

참조 구조에서 원천 메시지와 표준화는 Kafka와 스트림 처리에 있습니다. 흐름을 한곳에서 보이도록 이 실습은 네 단계를 모두 ClickHouse 안에 두고 Materialized View로 잇습니다.

네 개 모두 oss_lake 데이터베이스(Atomic)의 테이블입니다.

"지난 1시간"은 now()가 아니라 max(params.anchor_ts)에서 끝납니다. 그래서 언제 열어도 같은 질문에 답하고, 라이브 데모는 버튼을 누를 때마다 기준 시각을 1분 옮깁니다. 운영 환경에서는 질의와 Refreshable MV가 now()를 씁니다. TTL은 실제로 동작합니다(벽시계 기준). 브론즈와 실버는 1일, 골드는 2일이고, 모두 일 단위 파티션에 ttl_only_drop_parts = 1이라 만료된 데이터를 다시 쓰지 않고 파트째 버립니다. 그래서 파티션 하나가 TTL보다 최대 하루 더 남을 수 있습니다. 오래된 컨테이너를 다시 열지 말고 실습을 다시 적재하세요.

만드는 중에 만난 잘못된 결과 (26.6–26.9)

초기의 tools/hol run 두 번이 같은 20행 검사에서 실패했습니다. 같은 1시간에 대해 실버가 브론즈보다 몇 행 적게 돌려준 것입니다. 원인(2026-10-18 측정): DateTime64(3) 기본 키 컬럼에서 event_ts < <DateTime 값> 조건이 키 조건 event_ts <= <그 값> - 1초로 바뀝니다 (< '2026-10-18 08:44:00'에 대해 EXPLAIN indexes = 1이 event_ts in (-Inf, 1792313039]를 보여 줌). 마지막 1초 안에서 시작하는 그래뉼(여기서는 08:43:59.003, 3,033행)은 건너뛰어져서, 같은 조건의 countIf는 세는 행이 WHERE에서는 사라집니다. 그래뉼 경계가 어디에 떨어지느냐에 달려 있어 실행마다 나타났다 사라졌습니다.

최소 재현: DateTime64(3) 컬럼 하나, index_granularity = 1000, 2 ms 간격 5,000행을 정각에서 3 ms 뒤부터 넣어 경계 직전 1초 안에서 그래뉼이 시작되게 한 뒤 WHERE ts < toDateTime('… 00:00:09'). 26.6.8.7, 26.8.22.13, 26.9.13.15에서 4,499행이 아닌 4,000행을, 25.8.33.6에서는 맞는 값을 돌려줍니다. 행이 정각에서 시작하면 그래뉼도 정각에서 시작해 결과가 맞습니다. 그래서 대충 만든 재현은 통과합니다 (2026-10-18 리뷰에서 26.9.13.15로 다시 확인). 이미 보고된 문제인지는 확인하지 않았습니다.

이 실습은 event_ts를 DateTime64(3) 경계(toDateTime64(…, 3))와 비교합니다. 그러면 키 조건이 (-Inf, '1792313040')이 되고, 버그가 나타났던 실행도 이 변경으로 통과했습니다. 골드의 bucket은 DateTime을 DateTime과 비교하므로 영향이 없습니다.

함정 하나: 원본과 더는 맞지 않는 집계 상태

AggregateFunction 컬럼의 인자 타입은 Nullable 여부까지 원본 컬럼과 맞아야 합니다. pitfall.sql이 임시 데이터베이스에서 재현합니다(tools/hol은 실행하지 않습니다. 일부러 실패합니다). 2026-10-18 측정:

  • 서버가 볼 수 있는 불일치는 CREATE에서 거부됩니다. Nullable(Float32)에 대한 avgState(rsrp)를 AggregateFunction(avg, Float32)에 넣는 MV는 25.8.33.6, 26.6.8.7, 26.8.22.13, 26.9.13.15에서 모두 CANNOT_CONVERT_TYPE으로 실패합니다.
  • 나중에 생긴 불일치는 거부되지 않습니다. 원본 컬럼이 Float32일 때 MV를 만들고, ALTER TABLE … MODIFY COLUMN rsrp Nullable(Float32)을 실행하면 성공하고, 그 뒤 INSERT가 모두 실패했습니다(26.9.13.15).

Code: 70. DB::Exception: Conversion from AggregateFunction(avg, Nullable(Float32)) to AggregateFunction(avg, Float32) is not supported: while converting source column avg_rsrp_st to destination column avg_rsrp_st: while pushing to view oss_pitfall.kpi_mv … (CANNOT_CONVERT_TYPE)

원본 행은 그래도 기록됐습니다(trace 2행, kpi 1행). 원본은 계속 늘고 집계만 조용히 멈춥니다.

이 실습의 골드 레이어는 rsrp를 단순 합계(count(rsrp), sum(ifNull(rsrp, 0)))로 두고 uniqState에는 Nullable이 아닌 해시를 넣어 이 함정을 피합니다. 상태 타입을 원본에 맞추는 방법 (AggregateFunction(avg, Nullable(Float32)))도 있습니다.

ClickHouse Cloud에서 (라이브 사이트)

https://oss-lake.clickhouse.kr/는 녹화가 아니라 실제 데이터입니다.

  • 레이크: AWS의 ClickHouse Cloud 서비스에 있는 oss_lake 데이터베이스. 2026-10-18 26.6.1에 cloud/load.py로 적재했습니다. 같은 01–05 파일에 docstring에 적은 Cloud 차이만 더한 것이고, 03–05의 검사는 거기서도 모두 통과했습니다.
  • 흐름: cloud/feed.sql이 Refreshable MV 두 개를 더합니다. feed_rmv가 1분마다 다음 1분을 만들고(멈췄다 다시 켜면 한 번에 최대 5분씩 따라잡고, 같은 1분을 두 번 넣지 않음), 이어서 anchor_rmv가 레이크의 '지금'을 옮깁니다. 서빙 새로 고침은 그 뒤에 돕니다. TTL은 01-schema.sql에 있습니다(브론즈·실버 1일, 골드 2일, 파트째 삭제). 그래서 흐름이 멈추지 않아도 레이크 크기가 일정합니다. params(1분에 1행)에는 걸지 않아, 오래 멈춰도 레이크의 시계가 비지 않습니다. feed start는 시계가 5분 넘게 뒤처져 있으면 1분 전으로 다시 맞춰, 빈 구간을 다시 만들지 않고 건너뜁니다. 라이브 데모는 3분 동안 새 1분이 없으면 "멈춤"으로 표시합니다.
  • 사이트: Vercel 프로젝트 oss-lake. 페이지는 정적입니다. api/index.py가 데모의 GET 엔드포인트를 읽기 전용 사용자 oss_reader로 내줍니다: readonly = 1, 20초·읽기 3천만 행·결과 20만 행 한도, 시간당 쿼터(질의 3,000개, 읽기 50억 행), 엣지 캐시 20초. 엣지 캐시 키가 URL 전체라서, 함수는 쿼리 문자열을 거부하고(400) 끝의 /는 돌려보냅니다(308). 둘 다 ClickHouse를 부르지 않습니다. 오류 응답은 고정 문구이고 자세한 내용은 함수 로그에만 남습니다. 쓰기 엔드포인트는 없습니다(POST는 405). 함수가 ClickHouse에 닿지 못하거나 쿼터를 다 쓰면 데모는 녹화한 몇 분으로 돌아갑니다. 페이지와 함수는 Content-Security-Policy(default-src 'self', 인라인 스크립트·스타일 허용, frame-ancestors 'none'), X-Frame-Options: DENY, 카메라·마이크·위치·결제·USB를 끈 Permissions-Policy를 함께 보냅니다 (vercel.json).
cd usecase/oss-network-quality-lake

2026-10-18 그 서비스(복제본 2개, 각 최소 8 GiB, vCPU 2개)에서 측정했습니다.

  • 적재 시간: 01은 9초, 02는 66초, 03은 15초, 04는 2초, 05는 12초.
  • 흐름은 실패한 새로 고침 없이 1분에 180,000행씩 들어갔고, 레이크의 '지금'은 현재 벽시계 1분 안에 있었습니다.
  • 함수를 거쳐(네트워크 포함) /api/q/1(브론즈)은 3.9초, /api/q/4(서빙)는 0.35초.
  • oss_reader로 쓰기를 시도하면 ACCESS_DENIED로 거부됐습니다.

만나며 고친 것: 인벤토리 Dictionary는 복제본마다 사본이 따로 있습니다. SYSTEM RELOAD DICTIONARY는 한 복제본만 다시 읽었고, 다른 복제본은 인벤토리가 비어 있을 때 읽은 사본을 그대로 들고 있어서 이력 적재의 실버 행이 모두 지역 없이 들어갔습니다. 05의 검사가 이를 잡았습니다. 이제 적재기는 ON CLUSTER 'default'로 다시 읽고, 모든 복제본이 인벤토리 전체를 가질 때까지 기다립니다. Dictionary는 5–10분마다 스스로 다시 읽기도 합니다(LIFETIME(MIN 300 MAX 600)). 지역 이름은 적재할 때 실버와 골드에 박히므로, 인벤토리를 바꾼 뒤에는 모든 복제본에서 다시 읽고 영향받은 구간을 다시 처리합니다.

05의 검사는 테이블 전체가 아니라 레이크의 '지금' 직전 완결된 1시간만 봅니다. 그래서 층마다 TTL이 달라도 적재하고 며칠 뒤에 다시 돌려도 맞습니다. 그 1시간이 끊기지 않았다고 가정하므로, feed start가 빈 구간을 건너뛴 직후라면 1시간 뒤에 다시 돌립니다. 브론즈 검사는 일부가 빠지거나 겹친 분뿐 아니라 통째로 빠진 분도 잡습니다(2026-10-18 로컬 레이크에서 1분을 지워 "bronze is missing a minute"를 확인).

언어

한국어가 원본입니다. site/i18n/{ko,en,ja,zh}.json은 언어마다 카탈로그 하나이며 설명 페이지와 데모가 함께 씁니다. build.py는 /(en), /ko/, /ja/, /zh/를 쓰고, 키 집합이 다르면 실패합니다 (확인: ja.json에서 cta.note를 빼자 ja.json: missing ['cta.note']로 멈춤). SQL, 테이블과 컬럼 이름은 번역하지 않습니다. 2026-10-18 브라우저에서 320px과 데스크톱 너비, 라이트와 다크, 네 언어 모두 확인했습니다.

다루지 않는 것

  • 규모: 2시간, 셀 약 2만 개. 크기가 아니라 흐름이 목적입니다.
  • 실제 probe 형식, 실제 IMSI 암호화, Kafka나 오브젝트 스토리지 적재: 브론즈는 SQL로 채웁니다.
  • 노트 사이트 게시(web을 설정하지 않음).
