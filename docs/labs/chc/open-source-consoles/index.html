Open-source ClickHouse consoles on SharedMergeTree

Five open-source web UIs for ClickHouse, run against one ClickHouse Cloud service with the same scenarios: what they show for SharedMergeTree tables, what happens with two replicas behind one endpoint, and what each one needs to be set up.

Verified on ClickHouse Cloud 26.8.1.608 (AWS ap-northeast-2, 2 replicas), 2026-11-08. The tools ran in Docker on a Mac with the images and settings tools.sh uses, against the service's public endpoint over HTTPS 8443, connected as the service's default user; 01-setup.sql and 99-cleanup.sql ran with clickhouse client, and the long query is the one in long-query.sh. The two scripts themselves were only checked with bash -n. The LibreDB column check also ran on OSS clickhouse local 26.4.5.143 and 26.8.36.3 the same day.

CH-UI. The table overview reads the engine as SharedMergeTree and shows 2,100,000 rows and 15.3 MB, with the stored SharedMergeTree('/clickhouse/tables/{uuid}/{shard}', '{replica}') DDL. Lineage draws events → daily_mv → daily and v_buy. The cluster topology page lists default with 2 replicas and all_groups.default with 3 (a replica of another service in the same warehouse is included), with internal pod names — keep that page out of shared screenshots.

chmonitor. A Cloud service has one endpoint in front of its replicas, and system.processes is per replica. Each refresh of the running list lands on one replica, so long-query.sh showed on one refresh and was gone on the next. Cloud does not give out per-replica addresses, so it cannot be pinned the way chmonitor allows with a comma list in CLICKHOUSE_HOST. Cloud's replica-aware routing (Enterprise, beta) keeps one routing value on one replica, but it picks the replica by hash and needs a header or SNI from the client; it was not tried with these tools. When the query was visible, the kill button worked: the toast said "Killed query", and the client ended with Code: 394 QUERY_WAS_CANCELLED (two runs). The "Queries by user" panel also lists Cloud's own service accounts (for example monitoring-internal, operator-internal) and ClickPipes accounts.

CH-Ops. Connections are added in its UI, and its first super admin must come from the environment (SUPER_ADMIN_1*; it does not start without them). The replication queue page knows SharedMergeTree, and Tables & Parts shows the engines correctly. It lists every database the account can see.

LibreDB Studio. Connects with SSL mode verify-system. On 26.8 the schema tree (2 tables, 1 view, 1 materialized view) and queries work. Its schema query reads system.tables.target_database, which 26.4 does not have (clickhouse local 26.4.5.143: 0 columns; 26.8.36.3: 1), so against a 26.4 server the tree fails with Code: 47 … Identifier 'mv.target_database' cannot be resolved while SQL still runs.

What to plan for on SharedMergeTree

  1. Per-replica screens need clusterAllReplicas. Running queries, query_log and server metrics are per replica. Behind one endpoint a tool sees whichever replica answered. Tools that query clusterAllReplicas(default, system.processes) see all of them; an account doing that needs READ ON REMOTE.
  2. Tool accounts. default has no global GRANT OPTION, so GRANT ALL fails. GRANT CURRENT GRANTS ON *.* TO … hands over what default has; for system.* it leaves out system.zookeeper (SHOW GRANTS prints a REVOKE for it).
  3. No replication queue. Pages built on system.replication_queue are empty, as they should be.
  4. AI features. CH-UI, chmonitor, CH-Ops, CloudBeaver and LibreDB all have one. Decide whether query text may go to an LLM provider before turning them on.
  5. Cloud has its own console. Monitoring and Query insights already cover the operations screens. On Cloud these tools earn their place for SQL editing, lineage and their own roles.

Run it

cd chc/open-source-consoles
cat > .env <<'ENV'
CH_HOST=<service>.<region>.aws.clickhouse.cloud
CH_USER=default
CH_PASSWORD=<password>
ENV
chmod 600 .env
set -a; . ./.env; set +a
clickhouse client --host "$CH_HOST" --port 9440 --secure --user default --password "$CH_PASSWORD" \
  --param_admin_pw='<Admin-pw-1!>' --param_ro_pw='<Ro-pw-1!>' --multiquery < 01-setup.sql
./tools.sh up          # localhost:18501-18505
./long-query.sh        # in another terminal, for S6
./tools.sh down
clickhouse client --host "$CH_HOST" --port 9440 --secure --user default --password "$CH_PASSWORD" --multiquery < 99-cleanup.sql

The tools' own admin password is in .tools.env (generated, gitignored). CH-Ops and LibreDB need the connection added in their UI (host, port 8443, HTTPS/SSL on). The service's IP access list must allow the machine running Docker.

CH-UI. 테이블 개요가 엔진을 SharedMergeTree로 읽고 2,100,000행, 15.3 MB를 보여 주며, 저장된 DDL SharedMergeTree('/clickhouse/tables/{uuid}/{shard}', '{replica}')도 그대로 나옵니다. 계보는 events → daily_mv → daily와 v_buy를 그립니다. 클러스터 구성 화면에는 default(replica 2개)와 all_groups.default(3개, 같은 warehouse의 다른 서비스 replica 포함)가 내부 pod 이름과 함께 나오니 공유용 캡처에서는 빼 두세요.

chmonitor. Cloud 서비스는 replica 앞에 endpoint가 하나이고 system.processes는 replica마다 따로입니다. 실행 중 목록은 새로 고칠 때마다 한 replica에 닿기 때문에 long-query.sh가 한 번은 보이고 다음에는 사라졌습니다. Cloud는 replica별 주소를 주지 않아 chmonitor의 CLICKHOUSE_HOST 쉼표 목록으로 고정할 수도 없습니다. Cloud의 replica-aware routing(Enterprise, 베타)은 같은 라우팅 값을 같은 replica로 보내 주지만 replica를 해시로 정하고 클라이언트가 헤더나 SNI를 넣어야 합니다. 이번에는 이 도구들과 시험하지 않았습니다. 보일 때 중지 버튼을 누르면 "Killed query" 알림이 뜨고 클라이언트는 Code: 394 QUERY_WAS_CANCELLED로 끝났습니다(두 번 확인). "Queries by user"에는 Cloud 자체 서비스 계정(monitoring-internal, operator-internal 등)과 ClickPipes 계정도 나옵니다.

CH-Ops. 연결은 화면에서 추가하고, 첫 super admin은 환경 변수(SUPER_ADMIN_1*)로만 만듭니다(없으면 시작하지 않습니다). 복제 큐 화면이 SharedMergeTree를 알아보고, Tables & Parts의 엔진도 맞습니다. 계정이 볼 수 있는 모든 데이터베이스가 나옵니다.

LibreDB Studio. SSL 모드 verify-system으로 붙습니다. 26.8에서는 스키마 트리(테이블 2, 뷰 1, MV 1)와 쿼리가 모두 됩니다. 스키마 쿼리가 system.tables.target_database를 읽는데 26.4에는 이 열이 없어서(clickhouse local 26.4.5.143: 0개, 26.8.36.3: 1개) 26.4 서버에서는 트리가 Code: 47 … Identifier 'mv.target_database' cannot be resolved로 깨지고 SQL 실행만 됩니다.

SharedMergeTree에서 챙길 것

  1. replica별 화면은 clusterAllReplicas가 있어야 한다. 실행 중 쿼리, query_log, 서버 지표는 replica별입니다. endpoint 하나 뒤에서는 응답한 replica만 보입니다. clusterAllReplicas(default, system.processes)로 읽는 도구라야 전부 보이고, 그 계정에는 READ ON REMOTE가 필요합니다.
  2. 도구용 계정. default에 전역 GRANT OPTION이 없어 GRANT ALL은 실패합니다. GRANT CURRENT GRANTS ON *.* TO …가 default의 권한을 넘겨 줍니다. system.*에 쓰면 system.zookeeper는 빠집니다(SHOW GRANTS에 REVOKE로 나옵니다).
  3. 복제 큐가 없다. system.replication_queue 기반 화면은 비어 있는 게 정상입니다.
  4. AI 기능. CH-UI, chmonitor, CH-Ops, CloudBeaver, LibreDB 모두 있습니다. 켜기 전에 쿼리 내용이 LLM 공급자로 나가도 되는지 정하세요.
  5. Cloud에는 자체 콘솔이 있다. 운영 화면은 Monitoring·Query insights가 이미 맡습니다. Cloud에서 이 도구들의 쓸모는 SQL 편집, 계보, 도구 자체 역할 쪽입니다.
